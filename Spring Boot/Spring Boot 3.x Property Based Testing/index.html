    Property-Based Testing In Spring Boot 3.x#

    What Is The Topic#

    • Property-based testing (PBT) is a testing technique where, instead of writing examples by hand, you describe the properties (invariants/rules) that your code must always satisfy, and the framework generates hundreds of random inputs to try to break them.
    • It complements — it does not replace — example-based testing (plain Spring Boot 3.x JunitTest 5 tests). Example tests document known cases; property tests hunt for the unknown edge cases you didn't think of.
    • In the Java / JUnit 5 world the de-facto PBT library is jqwik. It plugs into the JUnit 5 Platform as its own TestEngine, so it runs side-by-side with your normal Jupiter tests.

    Example-Based vs Property-Based#

    • A quick comparison to frame the mindset shift:
    Aspect Example-Based (JUnit) Property-Based (jqwik)
    Input You hand-pick specific values. The framework generates many random values.
    What you assert "For input X, output is Y." "For all inputs, this rule holds."
    Edge cases Only the ones you remember. Found automatically (empty, zero, negatives, huge, unicode...).
    On failure Shows the one failing case. Shrinks to the smallest failing case.
    Best for Concrete known scenarios, documentation. Algorithms, parsers, serializers, invariants, math-like logic.
    • Mental model: stop asking "what is the answer for this input?" and start asking "what must be true for every possible input?"

    The "Properties" Mindset#

    • The hardest part of PBT is finding good properties. These recurring patterns help:
    Pattern Idea Example
    Round-trip (inverse) decode(encode(x)) == x JSON serialize → deserialize returns the original.
    Invariant Something is always true of the output. A sorted list has the same size & elements as the input.
    Idempotence Doing it twice == doing it once. trim(trim(s)) == trim(s); normalize(normalize(x)).
    Commutativity Order doesn't matter. add(a, b) == add(b, a).
    Oracle / model Compare against a simpler, known-correct implementation. Your fast algorithm vs. a naive brute-force one.
    Hard-to-prove, easy-to-verify Generating the answer is hard, checking it is easy. A factorization is correct if the factors multiply back.

    Project Setup#

    • jqwik is not included in spring-boot-starter-test, so add it explicitly with test scope.
    • Maven:
    <dependency>
    <groupId>net.jqwik</groupId>
    <artifactId>jqwik</artifactId>
    <version>1.9.1</version>
    <scope>test</scope>
</dependency>
    • Gradle (Kotlin DSL):
    testImplementation("net.jqwik:jqwik:1.9.1")

    Tip: spring-boot-starter-test pulls in junit-jupiter. jqwik registers its own engine on the JUnit Platform, so @Test (Jupiter) and @Property (jqwik) classes coexist in the same module and run together with mvn test.

    The Example Code Under Test#

    • We reuse the Product domain from the Spring Boot 3.x JunitTest 5 note and add a small piece of pure logic worth property-testing.
    // PriceCalculator.java
package com.example.demo.product;

import java.math.BigDecimal;
import java.math.RoundingMode;

public class PriceCalculator {

    /** Apply a percentage discount (0..100) to a price. */
    public BigDecimal applyDiscount(BigDecimal price, int percent) {
        if (percent < 0 || percent > 100) {
            throw new IllegalArgumentException("percent must be 0..100");
        }
        BigDecimal factor = BigDecimal.valueOf(100 - percent)
                                      .divide(BigDecimal.valueOf(100));
        return price.multiply(factor).setScale(2, RoundingMode.HALF_UP);
    }
}

    Step 1 — Your First Property#

    • A property is a method annotated with @Property (instead of @Test). Parameters annotated with @ForAll are filled by jqwik with generated values. By default jqwik runs each property 1000 times with different inputs.
    import net.jqwik.api.*;
import net.jqwik.api.constraints.*;

import java.math.BigDecimal;

import static org.assertj.core.api.Assertions.assertThat;

class PriceCalculatorPropertyTest {

    private final PriceCalculator calculator = new PriceCalculator();

    @Property
    void discountedPriceIsNeverGreaterThanOriginal(
            @ForAll @BigRange(min = "0", max = "100000") BigDecimal price,
            @ForAll @IntRange(min = 0, max = 100) int percent) {

        BigDecimal result = calculator.applyDiscount(price, percent);

        // PROPERTY: a discount can only reduce (or keep) the price
        assertThat(result).isLessThanOrEqualTo(price);
    }
}
    • What just happened: jqwik generated ~1000 (price, percent) pairs — including tricky ones like 0, 100000, percent=0, percent=100 — and checked the rule for every one. You wrote one method but tested a thousand cases.

    Step 2 — Reading A Failure & Shrinking#

    • jqwik's killer feature is shrinking. When a property fails, it doesn't just report the random input that broke it — it automatically searches for the smallest, simplest input that still fails, which usually points straight at the bug.
    • Example: suppose we wrongly asserted that a discount is always strictly less than the original (forgetting percent = 0):
    @Property
void buggy_discountIsStrictlyLess(
        @ForAll @BigRange(min = "1", max = "1000") BigDecimal price,
        @ForAll @IntRange(min = 0, max = 100) int percent) {
    assertThat(calculator.applyDiscount(price, percent)).isLessThan(price); // wrong!
}
    • A typical jqwik failure report:
    PriceCalculatorPropertyTest:buggy_discountIsStrictlyLess =
  org.opentest4j.AssertionFailedError:
    Expecting actual: 1.00 to be less than: 1.00

  |-------------------jqwik-------------------
  tries = 14            | # of calls to property
  checks = 14           | # of not rejected calls
  seed = 7261...        | reproduce with this seed
  Shrunk Sample (3 steps)
    price:   1
    percent: 0
    • jqwik shrank the failure down to price = 1, percent = 0 — instantly revealing that the property breaks when no discount is applied. The seed lets you reproduce the exact run deterministically.

    Step 3 — Generators (Arbitrary) & Constraints#

    • jqwik knows how to generate primitives, String, BigDecimal, collections, enums, etc. You shape the generated values with constraint annotations or with the Arbitraries factory.
    • Common constraint annotations:
    Annotation Applies to Example
    @IntRange(min, max) int/Integer @IntRange(min = 0, max = 100)
    @BigRange(min, max) BigDecimal/BigInteger @BigRange(min = "0", max = "1E6")
    @Positive / @Negative numbers non-zero positive/negative
    @StringLength(min, max) String bound the length
    @AlphaChars, @Chars(...) String restrict the alphabet
    @Size(min, max) collections list/set size bounds
    @NotBlank String reject blank strings
    • For richer control, build an Arbitrary programmatically and expose it with @Provide:
    import net.jqwik.api.*;
import java.math.BigDecimal;

class ArbitraryExamples {

    @Property
    void priceIsAlwaysTwoDecimalPlaces(@ForAll("validPrices") BigDecimal price) {
        // 'validPrices' refers to the @Provide method below by name
        // ... assert something about price
    }

    @Provide
    Arbitrary<BigDecimal> validPrices() {
        return Arbitraries.bigDecimals()
                .between(BigDecimal.ZERO, new BigDecimal("100000"))
                .ofScale(2);          // exactly 2 decimal places
    }
}
    • Transforming arbitraries — the building blocks you will use constantly:
      • .map(...) — transform each generated value (e.g. ints -> "ID-" + i).
      • .filter(...) — keep only values that match a predicate (use sparingly; heavy filtering is slow).
      • .flatMap(...) — make one generated value depend on another.
      • Combinators.combine(a, b).as(...) — build a composite object from several arbitraries.

    Step 4 — Generating Custom Domain Objects#

    • To property-test logic that takes a Product, teach jqwik how to build random valid Products using Combinators:
    import net.jqwik.api.*;
import java.math.BigDecimal;

import static org.assertj.core.api.Assertions.assertThat;

class ProductPropertyTest {

    @Property
    void anyValidProductHasNonNegativePrice(@ForAll("products") Product product) {
        assertThat(product.getPrice()).isGreaterThanOrEqualTo(BigDecimal.ZERO);
    }

    @Provide
    Arbitrary<Product> products() {
        Arbitrary<String> names = Arbitraries.strings()
                .alpha().ofMinLength(1).ofMaxLength(30);

        Arbitrary<BigDecimal> prices = Arbitraries.bigDecimals()
                .between(BigDecimal.ZERO, new BigDecimal("9999.99"))
                .ofScale(2);

        // combine the two arbitraries into a Product
        return Combinators.combine(names, prices).as(Product::new);
    }
}
    • This single @Provide becomes a reusable value factory for every property that needs a Product.

    Step 5 — Assumptions (Filtering Inputs At Runtime)#

    • Sometimes a property only holds under a precondition. Use Assume.that(...) to discard generated inputs that don't meet it, instead of failing.
    import net.jqwik.api.*;

@Property
void divisionRoundsTowardZeroForNonZeroDivisors(
        @ForAll int a, @ForAll int b) {

    Assume.that(b != 0);          // skip the b == 0 cases entirely

    int q = a / b;
    assertThat(q * b).isLessThanOrEqualTo(Math.abs(a) + Math.abs(b));
}
    • Caution: if assumptions reject too many inputs, jqwik can't gather enough valid samples and will report a generation failure. When you find yourself filtering aggressively, prefer building a constrained generator (Step 3) that only produces valid inputs in the first place.

    Step 6 — A Classic Round-Trip Property (Serialization)#

    • One of the most valuable PBT patterns in real Spring apps: serialize → deserialize must return an equal object. This catches subtle Jackson mapping bugs that hand-written examples miss.
    import com.fasterxml.jackson.databind.ObjectMapper;
import net.jqwik.api.*;

import static org.assertj.core.api.Assertions.assertThat;

class ProductJsonRoundTripTest {

    private final ObjectMapper mapper = new ObjectMapper();

    @Property
    void jsonSerializationIsLossless(@ForAll("products") Product original)
            throws Exception {

        String json = mapper.writeValueAsString(original);
        Product restored = mapper.readValue(json, Product.class);

        // ROUND-TRIP PROPERTY: decode(encode(x)) == x
        assertThat(restored.getName()).isEqualTo(original.getName());
        assertThat(restored.getPrice()).isEqualByComparingTo(original.getPrice());
    }

    @Provide
    Arbitrary<Product> products() {
        return Combinators.combine(
                Arbitraries.strings().alpha().ofMinLength(1).ofMaxLength(30),
                Arbitraries.bigDecimals().between(java.math.BigDecimal.ZERO,
                        new java.math.BigDecimal("9999.99")).ofScale(2)
        ).as(Product::new);
    }
}

    Step 7 — The Oracle Pattern (Model-Based)#

    • When you have a fast/complex implementation, verify it against a simpler, obviously-correct "oracle". Here we test a custom sort against the JDK's sort.
    import net.jqwik.api.*;
import java.util.*;

import static org.assertj.core.api.Assertions.assertThat;

class SortOraclePropertyTest {

    @Property
    void mySortMatchesJdkSort(@ForAll List<@ForAll Integer> input) {
        List<Integer> mine = MySorter.sort(new ArrayList<>(input));

        List<Integer> oracle = new ArrayList<>(input);
        Collections.sort(oracle);     // the trusted reference

        assertThat(mine).isEqualTo(oracle);
    }

    // Bonus: a pure invariant — output is a permutation of the input
    @Property
    void sortPreservesElements(@ForAll List<@ForAll Integer> input) {
        List<Integer> sorted = MySorter.sort(new ArrayList<>(input));
        assertThat(sorted).hasSameSizeAs(input);
        assertThat(sorted).containsExactlyInAnyOrderElementsOf(input);
    }
}

    Step 8 — Using PBT With A Spring Service#

    • jqwik runs without a Spring context by default (and that's good — properties should be fast and pure). For logic that genuinely needs Spring beans, you have two practical options:

    • Option A (recommended): keep properties on pure logic. Extract the rule-heavy code into a plain class (like PriceCalculator) and property-test it directly — no Spring needed. This is the fastest and most common approach.

    • Option B: bridge into a Spring context using the spring-test support module when a property must exercise wired beans:

    <dependency>
    <groupId>net.jqwik</groupId>
    <artifactId>jqwik-spring</artifactId>
    <version>0.11.0</version>
    <scope>test</scope>
</dependency>

    import net.jqwik.api.*;
import net.jqwik.spring.JqwikSpringSupport;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;

import static org.assertj.core.api.Assertions.*;

@JqwikSpringSupport          // bridges jqwik's lifecycle into Spring's TestContext
@SpringBootTest
class ProductServicePropertyTest {

    @Autowired
    private ProductService service;   // a real, wired Spring bean

    @Property(tries = 50)             // fewer tries — context calls are heavier
    void creatingThenFetchingReturnsSameProduct(@ForAll("products") Product input) {
        Product saved = service.create(input);
        Product fetched = service.getById(saved.getId());

        assertThat(fetched.getName()).isEqualTo(input.getName());
    }

    @Provide
    Arbitrary<Product> products() {
        return Combinators.combine(
                Arbitraries.strings().alpha().ofMinLength(1).ofMaxLength(20),
                Arbitraries.bigDecimals().between(java.math.BigDecimal.ZERO,
                        new java.math.BigDecimal("9999.99")).ofScale(2)
        ).as(Product::new);
    }
}
    • Note: lower the tries count when a property touches a database or full context — 1000 context round-trips would be painfully slow. PBT shines brightest on pure logic; use Option B sparingly.

    Step 9 — Tuning & Reproducibility#

    • Useful @Property attributes and configuration:
    Setting What it does
    @Property(tries = 500) Number of generated cases (default 1000).
    @Property(seed = "42") Fix the random seed for a fully deterministic run.
    @Property(shrinking = ShrinkingMode.FULL) Control the shrinking strategy.
    @Report(Reporting.GENERATED) Print every generated sample (debugging).
    @StatisticsReport + Statistics.collect(...) Measure the distribution of your generated data — verify edge cases actually appear.
    • A junit-platform.properties file in src/test/resources can set global defaults:
    jqwik.tries.default = 1000
jqwik.database = .jqwik-database     # remembers failing seeds across runs
jqwik.failures.after.default = SAMPLE_ONLY  # re-run last failing sample first
    • jqwik.database is a quiet superpower: jqwik records failing samples to disk and replays them first on the next run, so once a property finds a bug it keeps reproducing it until you fix it.

    When To Use (And Not Use) PBT#

    • Great fit:
      • Pure functions, algorithms, parsers, encoders/serializers.
      • Code with clear invariants (sorting, validation, math, money calculations).
      • Round-trip conversions (DTO ↔ entity, JSON ↔ object).
    • Poor fit:
      • Heavy I/O / external services where each "try" is slow or non-deterministic.
      • Code whose "correct answer" is just a lookup table (example tests are clearer there).
    • Best practice: use PBT alongside example tests — properties for the general rules, a few hand-written examples for documentation and known regressions.

    Best Practices#

    • Start with one strong invariant per piece of logic, then add more property patterns (round-trip, oracle, idempotence).
    • Prefer constrained generators over heavy Assume.that filtering — generate valid data, don't discard invalid data.
    • Make @Provide arbitraries reusable across properties to avoid duplication.
    • Trust the shrinker: when a property fails, read the shrunk sample first — it is the minimal reproduction.
    • Pin the seed to reproduce a CI failure locally; enable jqwik.database so failures stick.
    • Keep properties pure and fast; reserve Spring-context properties (Option B) for the rare cases that truly need them, with a low tries count.
