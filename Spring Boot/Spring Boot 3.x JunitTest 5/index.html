    JUnit 5 In Spring Boot 3.x#

    What Is The Topic#

    • JUnit 5 is the de-facto standard testing framework for Java. It is the successor of JUnit 4 and is the default testing engine that ships with Spring Boot 3.x (which requires Java 17+).
    • This note is a hands-on, step-by-step guide. We start from the simplest possible unit test (no Spring at all) and progressively move toward full integration testing with a real database using Testcontainers.
    • Throughout the guide we use one coherent example application — a small Product management service — so each step builds on the previous one.

    JUnit 5 Architecture#

    • Unlike JUnit 4 (a single jar), JUnit 5 is composed of three sub-projects. Understanding this helps a lot when you read stack traces or configure dependencies.
    Module Description
    JUnit Platform The foundation that launches testing frameworks on the JVM. It defines the TestEngine API and is what your IDE / build tool talks to.
    JUnit Jupiter The new programming model and extension model for writing tests in JUnit 5. This is where annotations like @Test, @BeforeEach, @ExtendWith live.
    JUnit Vintage A TestEngine that runs old JUnit 3 and JUnit 4 tests on the JUnit 5 platform, so you can migrate gradually.
    • Key takeaway: when you write a "JUnit 5 test", you are really writing a JUnit Jupiter test.

    Project Setup#

    • In Spring Boot 3.x you only need one dependency to get the whole testing stack:
    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-test</artifactId>
    <scope>test</scope>
</dependency>
    • This single starter transitively pulls in everything you typically need for testing:
    Library Purpose
    JUnit 5 (Jupiter) The test framework / engine.
    Spring Test & Spring Boot Test Utilities and integration support (@SpringBootTest, MockMvc, slices, etc.).
    AssertJ Fluent assertions: assertThat(x).isEqualTo(y).
    Mockito Mocking framework for isolating the unit under test.
    Hamcrest Matchers, often used with MockMvc.
    JSONassert / JsonPath Asserting on JSON responses.

    Spring Boot 3.x removed JUnit Vintage from the starter. If you still have JUnit 4 tests, add junit-vintage-engine explicitly — otherwise old tests are simply not picked up.

    JUnit 5 Core Annotations#

    • The annotations you will use most often, all from the org.junit.jupiter.api package:
    Annotation Description
    @Test Marks a method as a test case.
    @BeforeEach / @AfterEach Runs before/after each test method — used for fresh setup/cleanup.
    @BeforeAll / @AfterAll Runs once before/after all tests in the class (must be static, unless lifecycle is PER_CLASS).
    @DisplayName("...") A human-readable name shown in test reports.
    @Disabled("reason") Temporarily skips a test.
    @Nested Groups related tests into an inner class for better organization.
    @ParameterizedTest Runs the same test multiple times with different inputs.
    @ExtendWith(...) Registers an extension (e.g. Mockito, Spring). Replaces JUnit 4's @RunWith.
    @Tag("...") Categorizes tests so you can filter them (e.g. slow, integration).

    The Example Application#

    • Here is the domain we will test. A simple Product with a service and a REST controller.
    // Product.java — JPA entity (note the jakarta.* namespace in Spring Boot 3)
package com.example.demo.product;

import jakarta.persistence.*;
import java.math.BigDecimal;

@Entity
@Table(name = "products")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private BigDecimal price;

    protected Product() { } // required by JPA

    public Product(String name, BigDecimal price) {
        this.name = name;
        this.price = price;
    }

    // getters / setters omitted for brevity
    public Long getId() { return id; }
    public String getName() { return name; }
    public BigDecimal getPrice() { return price; }
    public void setName(String name) { this.name = name; }
    public void setPrice(BigDecimal price) { this.price = price; }
}

    // ProductRepository.java
package com.example.demo.product;

import org.springframework.data.jpa.repository.JpaRepository;
import java.util.Optional;

public interface ProductRepository extends JpaRepository<Product, Long> {
    Optional<Product> findByName(String name);
}

    // ProductService.java — the business logic we want to unit-test
package com.example.demo.product;

import org.springframework.stereotype.Service;

@Service
public class ProductService {

    private final ProductRepository repository;

    public ProductService(ProductRepository repository) {
        this.repository = repository;
    }

    public Product getById(Long id) {
        return repository.findById(id)
                .orElseThrow(() -> new ProductNotFoundException(id));
    }

    public Product create(Product product) {
        if (product.getPrice().signum() < 0) {
            throw new IllegalArgumentException("Price cannot be negative");
        }
        return repository.save(product);
    }
}

    // ProductNotFoundException.java
package com.example.demo.product;

public class ProductNotFoundException extends RuntimeException {
    public ProductNotFoundException(Long id) {
        super("Product not found with id: " + id);
    }
}

    Step 1 — Your First Unit Test (No Spring)#

    • The fastest, cheapest tests don't touch Spring at all. Let's add a tiny piece of pure logic and test it directly.
    // PriceCalculator.java
package com.example.demo.product;

import java.math.BigDecimal;

public class PriceCalculator {
    public BigDecimal applyDiscount(BigDecimal price, int percent) {
        if (percent < 0 || percent > 100) {
            throw new IllegalArgumentException("percent must be 0..100");
        }
        BigDecimal factor = BigDecimal.valueOf(100 - percent)
                                      .divide(BigDecimal.valueOf(100));
        return price.multiply(factor);
    }
}

    // PriceCalculatorTest.java
package com.example.demo.product;

import org.junit.jupiter.api.DisplayName;
import org.junit.jupiter.api.Test;

import java.math.BigDecimal;

import static org.junit.jupiter.api.Assertions.assertEquals;

class PriceCalculatorTest {

    private final PriceCalculator calculator = new PriceCalculator();

    @Test
    @DisplayName("10% off 100 should be 90")
    void applyDiscount_returnsDiscountedPrice() {
        // given
        BigDecimal price = new BigDecimal("100.00");

        // when
        BigDecimal result = calculator.applyDiscount(price, 10);

        // then
        assertEquals(0, new BigDecimal("90.00").compareTo(result));
    }
}
    • Notes:
      • Test classes and methods can be package-private (no public needed) in JUnit 5.
      • The given / when / then comment structure (a.k.a. Arrange-Act-Assert) keeps tests readable.
      • We compare BigDecimal with compareTo (returns 0) because assertEquals on BigDecimal also checks scale (90.0 ≠ 90.00).

    Step 2 — Assertions In Depth#

    • JUnit 5 assertions live in org.junit.jupiter.api.Assertions. The most useful ones:
    import static org.junit.jupiter.api.Assertions.*;

@Test
void assertionShowcase() {
    // equality / truth
    assertEquals(4, 2 + 2);
    assertTrue(5 > 1);
    assertNull(null);

    // grouped assertions — all are evaluated, failures reported together
    var product = new Product("Pen", new BigDecimal("1.50"));
    assertAll("product",
        () -> assertEquals("Pen", product.getName()),
        () -> assertEquals(new BigDecimal("1.50"), product.getPrice())
    );

    // exception assertions
    var ex = assertThrows(IllegalArgumentException.class,
        () -> new PriceCalculator().applyDiscount(BigDecimal.TEN, 200));
    assertEquals("percent must be 0..100", ex.getMessage());

    // timeout
    assertTimeout(java.time.Duration.ofMillis(100), () -> { /* fast code */ });
}
    • Spring Boot also bundles AssertJ, which many developers prefer for its fluent, readable chains:
    import static org.assertj.core.api.Assertions.assertThat;

assertThat(product.getName()).isEqualTo("Pen");
assertThat(product.getPrice()).isEqualByComparingTo("1.50");
assertThat(List.of("a", "b")).hasSize(2).contains("a");

    Step 3 — Lifecycle Methods#

    • Use lifecycle hooks to set up and tear down state, keeping each test isolated.
    import org.junit.jupiter.api.*;

class LifecycleDemoTest {

    @BeforeAll
    static void initAll() {
        System.out.println("Runs ONCE before all tests");
    }

    @BeforeEach
    void init() {
        System.out.println("Runs before EACH test — fresh fixture here");
    }

    @Test
    void testOne() { /* ... */ }

    @Test
    void testTwo() { /* ... */ }

    @AfterEach
    void tearDown() {
        System.out.println("Runs after EACH test — cleanup here");
    }

    @AfterAll
    static void tearDownAll() {
        System.out.println("Runs ONCE after all tests");
    }
}
    • Rule of thumb: create your fresh objects in @BeforeEach, not as field initializers shared across tests, to avoid state leaking between test methods.

    Step 4 — Parameterized Tests#

    • Instead of copy-pasting a test for each input, run it once with many inputs. Requires the junit-jupiter-params artifact (already included by the Spring Boot starter).
    import org.junit.jupiter.params.ParameterizedTest;
import org.junit.jupiter.params.provider.*;

import java.math.BigDecimal;
import java.util.stream.Stream;

import static org.junit.jupiter.api.Assertions.assertEquals;

class DiscountParameterizedTest {

    private final PriceCalculator calculator = new PriceCalculator();

    // 1) Simple single-argument source
    @ParameterizedTest
    @ValueSource(ints = {0, 50, 100})
    void validPercentsDoNotThrow(int percent) {
        calculator.applyDiscount(BigDecimal.TEN, percent); // no exception expected
    }

    // 2) CSV source — multiple typed arguments per run
    @ParameterizedTest(name = "{0} with {1}% off = {2}")
    @CsvSource({
        "100.00, 10, 90.00",
        "200.00, 50, 100.00",
        "50.00,  0,  50.00"
    })
    void appliesDiscountCorrectly(BigDecimal price, int percent, BigDecimal expected) {
        assertEquals(0, expected.compareTo(calculator.applyDiscount(price, percent)));
    }

    // 3) Method source — when arguments need real objects / logic
    @ParameterizedTest
    @MethodSource("priceProvider")
    void methodSourceExample(BigDecimal price, BigDecimal expected) {
        assertEquals(0, expected.compareTo(calculator.applyDiscount(price, 10)));
    }

    static Stream<Arguments> priceProvider() {
        return Stream.of(
            Arguments.of(new BigDecimal("100"), new BigDecimal("90")),
            Arguments.of(new BigDecimal("10"),  new BigDecimal("9"))
        );
    }
}
    • Other useful sources: @EnumSource, @NullSource, @EmptySource, @NullAndEmptySource, and @CsvFileSource (reads a CSV from src/test/resources).

    Step 5 — Testing The Service Layer With Mockito#

    • The ProductService depends on ProductRepository. In a unit test we don't want a real database — we mock the repository so we test the service logic in isolation.
    import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.InjectMocks;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

import java.math.BigDecimal;
import java.util.Optional;

import static org.assertj.core.api.Assertions.*;
import static org.mockito.Mockito.*;

@ExtendWith(MockitoExtension.class)   // wires Mockito into JUnit 5
class ProductServiceTest {

    @Mock
    private ProductRepository repository;     // a fake collaborator

    @InjectMocks
    private ProductService service;           // mocks injected into this

    @Test
    void getById_whenFound_returnsProduct() {
        // given — define the mock's behavior (stubbing)
        Product stored = new Product("Laptop", new BigDecimal("999.00"));
        when(repository.findById(1L)).thenReturn(Optional.of(stored));

        // when
        Product result = service.getById(1L);

        // then
        assertThat(result.getName()).isEqualTo("Laptop");
        verify(repository).findById(1L);   // verify the interaction happened
    }

    @Test
    void getById_whenMissing_throws() {
        when(repository.findById(99L)).thenReturn(Optional.empty());

        assertThatThrownBy(() -> service.getById(99L))
            .isInstanceOf(ProductNotFoundException.class)
            .hasMessageContaining("99");
    }

    @Test
    void create_withNegativePrice_throwsAndNeverSaves() {
        Product invalid = new Product("Bad", new BigDecimal("-1"));

        assertThatThrownBy(() -> service.create(invalid))
            .isInstanceOf(IllegalArgumentException.class);

        verify(repository, never()).save(any()); // ensure we short-circuited
    }
}
    • Key Mockito ideas:
      • @Mock creates a fake; @InjectMocks builds the real object and injects the mocks.
      • when(...).thenReturn(...) stubs behavior; verify(...) asserts an interaction occurred.
      • This test is fast — no Spring context, no database. Prefer this style for business logic.

    Step 6 — Testing The Web Layer With @WebMvcTest#

    • A test slice loads only part of the Spring context. @WebMvcTest boots the MVC layer (controllers, JSON, filters) but not services or repositories — you mock those.
    // ProductController.java
@RestController
@RequestMapping("/api/products")
public class ProductController {

    private final ProductService service;

    public ProductController(ProductService service) {
        this.service = service;
    }

    @GetMapping("/{id}")
    public Product getById(@PathVariable Long id) {
        return service.getById(id);
    }
}

    import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.WebMvcTest;
import org.springframework.boot.test.mock.mockito.MockBean;
import org.springframework.test.web.servlet.MockMvc;

import java.math.BigDecimal;

import static org.mockito.Mockito.when;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@WebMvcTest(ProductController.class)
class ProductControllerTest {

    @Autowired
    private MockMvc mockMvc;          // simulate HTTP without starting a server

    @MockBean
    private ProductService service;   // replaces the real bean in the context

    @Test
    void getById_returns200AndJson() throws Exception {
        when(service.getById(1L))
            .thenReturn(new Product("Laptop", new BigDecimal("999.00")));

        mockMvc.perform(get("/api/products/1"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.name").value("Laptop"))
            .andExpect(jsonPath("$.price").value(999.00));
    }
}
    • Notes:
      • MockMvc performs requests inside the Spring MVC machinery without binding a real port — fast and deterministic.
      • @MockBean puts a Mockito mock into the application context, replacing the real ProductService.
      • jsonPath (from JsonPath, bundled by the starter) lets you assert on the JSON body.
      • In Spring Boot 3.4+, @MockBean is deprecated in favor of @MockitoBean — same idea, new package.

    Step 7 — Testing The Persistence Layer With @DataJpaTest#

    • @DataJpaTest is another slice that configures only JPA: repositories, an in-memory database (H2 by default), and a TestEntityManager. Each test runs in a transaction that is rolled back afterwards, keeping tests isolated.
    import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.boot.test.autoconfigure.orm.jpa.TestEntityManager;

import java.math.BigDecimal;
import java.util.Optional;

import static org.assertj.core.api.Assertions.assertThat;

@DataJpaTest
class ProductRepositoryTest {

    @Autowired
    private TestEntityManager entityManager;  // helper to seed test data

    @Autowired
    private ProductRepository repository;

    @Test
    void findByName_returnsMatchingProduct() {
        // given — persist directly via the entity manager
        entityManager.persistAndFlush(new Product("Keyboard", new BigDecimal("49.99")));

        // when
        Optional<Product> found = repository.findByName("Keyboard");

        // then
        assertThat(found).isPresent();
        assertThat(found.get().getPrice()).isEqualByComparingTo("49.99");
    }
}
    • Add an in-memory DB for the test scope so H2 is on the classpath:
    <dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <scope>test</scope>
</dependency>

    Step 8 — Full Integration Test With @SpringBootTest#

    • When you want to test the application end to end — controller → service → repository → database — use @SpringBootTest, which loads the entire application context.
    import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.web.servlet.AutoConfigureMockMvc;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.test.web.servlet.MockMvc;

import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.*;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.*;

@SpringBootTest                 // loads the FULL application context
@AutoConfigureMockMvc           // gives us a MockMvc against the real beans
class ProductIntegrationTest {

    @Autowired
    private MockMvc mockMvc;

    @Test
    void createThenFetch_worksEndToEnd() throws Exception {
        // create
        String body = """
            { "name": "Monitor", "price": 250.00 }
            """;

        mockMvc.perform(post("/api/products")
                .contentType("application/json")
                .content(body))
            .andExpect(status().isOk());

        // fetch
        mockMvc.perform(get("/api/products/1"))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.name").value("Monitor"));
    }
}
    • @SpringBootTest web environment options (the webEnvironment attribute):
      • MOCK (default) — mock servlet environment, used with MockMvc.
      • RANDOM_PORT / DEFINED_PORT — start a real embedded server; inject TestRestTemplate or WebTestClient to make real HTTP calls.
    @SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class RealServerTest {

    @Autowired
    private org.springframework.boot.test.web.client.TestRestTemplate restTemplate;

    @Test
    void getProduct_overRealHttp() {
        var response = restTemplate.getForEntity("/api/products/1", Product.class);
        // assert on response.getStatusCode(), response.getBody() ...
    }
}
    • Trade-off: @SpringBootTest is the most realistic but the slowest (it boots the whole app). Use slices (Steps 5–7) for the majority of tests and reserve full integration tests for critical happy-paths. This is the classic test pyramid: many fast unit tests, fewer slice tests, a handful of full integration tests.

    Step 9 (Hard) — Real Database Integration With Testcontainers#

    • H2 is convenient but it is not your production database. Subtle SQL differences can hide bugs. Testcontainers spins up a throwaway real PostgreSQL in Docker for the duration of the test.

    • Dependencies:

    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-testcontainers</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>postgresql</artifactId>
    <scope>test</scope>
</dependency>
<dependency>
    <groupId>org.testcontainers</groupId>
    <artifactId>junit-jupiter</artifactId>
    <scope>test</scope>
</dependency>
    • The test (Spring Boot 3.1+ style using @ServiceConnection, which auto-wires the datasource URL/credentials from the container):
    import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

import java.math.BigDecimal;

import static org.assertj.core.api.Assertions.assertThat;

@SpringBootTest
@Testcontainers
class ProductTestcontainersIT {

    @Container
    @ServiceConnection   // Spring Boot 3.1+: no manual datasource config needed
    static PostgreSQLContainer<?> postgres =
        new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired
    private ProductService service;

    @Test
    void savesToRealPostgres() {
        Product saved = service.create(new Product("SSD", new BigDecimal("120.00")));
        assertThat(saved.getId()).isNotNull();

        Product fetched = service.getById(saved.getId());
        assertThat(fetched.getName()).isEqualTo("SSD");
    }
}
    • Notes:
      • @Container + static means the container is started once for the whole class (much faster than per-method).
      • Before Spring Boot 3.1 you wired the container manually with @DynamicPropertySource:
    @DynamicPropertySource
static void props(DynamicPropertyRegistry registry) {
    registry.add("spring.datasource.url", postgres::getJdbcUrl);
    registry.add("spring.datasource.username", postgres::getUsername);
    registry.add("spring.datasource.password", postgres::getPassword);
}
    • Requires a running Docker daemon on the machine / CI runner.
    • By convention, integration tests are suffixed *IT and often run in a separate Maven phase via the Failsafe plugin.

    Running The Tests#

    • With Maven:
    mvn test                       # run unit tests (Surefire)
mvn verify                     # also run *IT integration tests (Failsafe)
mvn test -Dtest=ProductServiceTest          # a single class
mvn test -Dtest=ProductServiceTest#getById_whenFound_returnsProduct  # one method
    • With Gradle:
    ./gradlew test
./gradlew test --tests "com.example.demo.product.ProductServiceTest"

    Best Practices#

    • Follow the test pyramid: lots of fast unit tests, some slice tests, few full integration tests.
    • One logical assertion per test (use assertAll to group related checks). A test should fail for exactly one reason.
    • Name tests by behavior: getById_whenMissing_throws reads better than test1. Use @DisplayName for reports.
    • Keep tests isolated and repeatable: no shared mutable state, no dependence on test ordering. Build fixtures in @BeforeEach.
    • Mock collaborators, not the class under test. If you find yourself mocking everything, the unit may be doing too much.
    • Prefer slices over @SpringBootTest when you only need one layer — they are dramatically faster.
    • Use @Nested and @Tag to organize and selectively run tests (e.g. exclude @Tag("slow") locally, run everything in CI).
    • Test the contract, not the implementation: assert on observable outputs and interactions, so refactors don't break tests needlessly.
