    JPA With Specification Query#

    What Is The Topic#

    • A Specification is Spring Data JPA's object-oriented wrapper around the JPA Criteria API. It lets you build type-safe, composable, dynamic queries in Java instead of concatenating JPQL strings or exploding your repository with dozens of findByAAndBAndC... methods.
    • Each Specification<T> is essentially a function that, given a Criteria Root, CriteriaQuery, and CriteriaBuilder, returns a Predicate (a WHERE-clause fragment). Because predicates are objects, you can combine them with and / or / not at runtime.
    • The killer use case is dynamic filtering / search screens: the user ticks some filters, leaves others blank, and you assemble exactly the query they asked for — no if-soup, no string building, no SQL injection.
    • In Spring Boot 3 / Hibernate 6 everything lives under the jakarta.persistence.criteria namespace. This note builds Specifications step by step: a first predicate, composition, a reusable filter builder, joins, sorting/paging, projections, and the metamodel for compile-time safety.
    • See JPA In Spring Boot and Hibernate for the underlying ORM concepts this note assumes.

    Why Specifications (vs The Alternatives)#

    • Spring Data gives you several ways to query. Specifications fill a specific gap:
    Approach Good for Falls down when
    Derived queries (findByNameAndStatus) A handful of fixed queries. Combinations explode; optional filters force many overloads.
    @Query (JPQL) A known, static query. Dynamic WHERE needs string building → brittle, unsafe.
    Specification Dynamic, composable filters built at runtime. A single, fixed query (overkill).
    QueryDSL Same niche, fluent DSL. Extra dependency + annotation processor + build setup.
    • Rule of thumb: fixed query → derived/@Query; dynamic query → Specification.

    How A Specification Works#

    • The contract is one method:
    public interface Specification<T> {
    Predicate toPredicate(Root<T> root,
                          CriteriaQuery<?> query,
                          CriteriaBuilder cb);
}
    Parameter What it is
    Root<T> The entity you query from — use it to reference columns: root.get("price").
    CriteriaQuery<?> The whole query — set ordering, distinct, grouping on it.
    CriteriaBuilder The factory for predicates and expressions: cb.equal(...), cb.greaterThan(...), cb.and(...).
    • You return a Predicate. Returning null means "no condition" — Spring Data treats it as always true, which is the trick that makes optional filters clean.

    Step 1 — Enable Specifications On The Repository#

    • Extend JpaSpecificationExecutor<T> alongside JpaRepository. That adds the findAll(Specification), count(Specification), findOne(Specification), and paged overloads.
    import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.jpa.repository.JpaSpecificationExecutor;

public interface ProductRepository
        extends JpaRepository<Product, Long>,
                JpaSpecificationExecutor<Product> {
}
    • The example entity used throughout:
    import jakarta.persistence.*;
import java.math.BigDecimal;
import java.time.LocalDate;

@Entity
@Table(name = "products")
public class Product {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private String category;
    private BigDecimal price;
    private boolean active;
    private LocalDate releasedOn;

    @ManyToOne
    @JoinColumn(name = "supplier_id")
    private Supplier supplier;

    // getters / setters omitted for brevity
}

    Step 2 — Your First Specification#

    • A Specification is just a lambda returning a Predicate. Here is "category equals X":
    import org.springframework.data.jpa.domain.Specification;

public class ProductSpecifications {

    public static Specification<Product> hasCategory(String category) {
        return (root, query, cb) -> cb.equal(root.get("category"), category);
    }
}
    • Use it:
    List<Product> books = productRepository.findAll(
        ProductSpecifications.hasCategory("BOOKS"));
    • root.get("category") references the column; cb.equal(...) builds the category = ? predicate. Spring runs it as a parameterized query — safe from SQL injection by construction.

    Step 3 — More Predicate Building Blocks#

    • The CriteriaBuilder covers every SQL operator. Keep each one a small static factory:
    public static Specification<Product> priceGreaterThan(BigDecimal min) {
    return (root, query, cb) -> cb.greaterThanOrEqualTo(root.get("price"), min);
}

public static Specification<Product> priceBetween(BigDecimal low, BigDecimal high) {
    return (root, query, cb) -> cb.between(root.get("price"), low, high);
}

public static Specification<Product> isActive() {
    return (root, query, cb) -> cb.isTrue(root.get("active"));
}

// Case-insensitive "contains" — note lower() on BOTH sides
public static Specification<Product> nameContains(String text) {
    return (root, query, cb) -> cb.like(
            cb.lower(root.get("name")),
            "%" + text.toLowerCase() + "%");
}

public static Specification<Product> releasedAfter(LocalDate date) {
    return (root, query, cb) -> cb.greaterThan(root.get("releasedOn"), date);
}

public static Specification<Product> categoryIn(Collection<String> categories) {
    return (root, query, cb) -> root.get("category").in(categories);
}
    SQL you want CriteriaBuilder call
    = cb.equal(path, value)
    <> cb.notEqual(path, value)
    > >= < <= cb.greaterThan / greaterThanOrEqualTo / lessThan / lessThanOrEqualTo
    BETWEEN cb.between(path, low, high)
    LIKE cb.like(path, pattern)
    IN (...) path.in(collection)
    IS NULL cb.isNull(path)
    AND / OR / NOT cb.and(...) / cb.or(...) / cb.not(...)

    Step 4 — Composing Specifications With and / or / not#

    • This is the whole point. Specification has static and default combinators, so predicates compose like LEGO:
    Specification<Product> spec =
        Specification.where(ProductSpecifications.hasCategory("BOOKS"))
                     .and(ProductSpecifications.priceGreaterThan(new BigDecimal("20")))
                     .and(ProductSpecifications.isActive());

List<Product> result = productRepository.findAll(spec);
// → WHERE category = 'BOOKS' AND price >= 20 AND active = true
    • Specification.where(...) is a null-safe entry point — if its argument is null, the chain still works. Combine with .and(), .or(), and .not():
    Specification<Product> cheapOrInactive =
        ProductSpecifications.priceGreaterThan(new BigDecimal("100"))
                .not()
                .or(Specification.not(ProductSpecifications.isActive()));

    Step 5 — Dynamic Filtering (The Real-World Use Case)#

    • A search endpoint gets a filter object where every field is optional. Build the Specification by appending only the filters that are present — null predicates simply drop out.
    public record ProductFilter(
        String category,
        BigDecimal minPrice,
        BigDecimal maxPrice,
        String nameLike,
        Boolean activeOnly) { }

    public static Specification<Product> fromFilter(ProductFilter f) {
    return (root, query, cb) -> {
        List<Predicate> predicates = new ArrayList<>();

        if (f.category() != null)
            predicates.add(cb.equal(root.get("category"), f.category()));

        if (f.minPrice() != null)
            predicates.add(cb.greaterThanOrEqualTo(root.get("price"), f.minPrice()));

        if (f.maxPrice() != null)
            predicates.add(cb.lessThanOrEqualTo(root.get("price"), f.maxPrice()));

        if (f.nameLike() != null && !f.nameLike().isBlank())
            predicates.add(cb.like(cb.lower(root.get("name")),
                    "%" + f.nameLike().toLowerCase() + "%"));

        if (Boolean.TRUE.equals(f.activeOnly()))
            predicates.add(cb.isTrue(root.get("active")));

        // Combine all collected predicates with AND
        return cb.and(predicates.toArray(Predicate[]::new));
    };
}
    • Only the filters the user actually supplied end up in the SQL. No string building, no if-branches generating different JPQL, fully parameterized.
    • cb.and(...) of an empty array evaluates to always true (returns all rows) — exactly the right behavior when no filter is given.

    Step 6 — Wire It Through Controller → Service → Repository#

    • Put it together with a clean layering: the controller only handles HTTP (bind params, return a response), the service owns the business logic (build the Specification, run it in a transaction), and the repository does data access. The controller never touches the repository directly.
    // 1. SERVICE — owns the query logic; the only layer that knows the repository
@Service
public class ProductService {

    private final ProductRepository repository;

    public ProductService(ProductRepository repository) {
        this.repository = repository;
    }

    @Transactional(readOnly = true)
    public Page<Product> search(ProductFilter filter, Pageable pageable) {
        return repository.findAll(
                ProductSpecifications.fromFilter(filter), pageable);
    }
}

    // 2. CONTROLLER — only HTTP concerns; delegates to the service
@RestController
@RequestMapping("/api/products")
public class ProductController {

    private final ProductService productService;

    public ProductController(ProductService productService) {
        this.productService = productService;
    }

    @GetMapping
    public Page<Product> search(
            @RequestParam(required = false) String category,
            @RequestParam(required = false) BigDecimal minPrice,
            @RequestParam(required = false) BigDecimal maxPrice,
            @RequestParam(required = false) String name,
            @RequestParam(required = false) Boolean activeOnly,
            Pageable pageable) {

        ProductFilter filter =
                new ProductFilter(category, minPrice, maxPrice, name, activeOnly);

        return productService.search(filter, pageable);
    }
}
    • GET /api/products?category=BOOKS&minPrice=20&activeOnly=true&page=0&size=20&sort=price,desc
    • Why this layering: the controller stays thin and easy to test (no DB), the service is where you put transactions (@Transactional), validation, mapping to DTOs, and reuse across multiple controllers. Injecting a repository straight into a controller couples HTTP to persistence and is widely considered an anti-pattern.
    • Spring binds Pageable from page/size/sort automatically and the paged findAll(spec, pageable) runs LIMIT/OFFSET + a COUNT query.

    Step 7 — Joins And Querying Related Entities#

    • To filter on an associated entity, join from the root. Filtering by the supplier's country:
    public static Specification<Product> supplierCountry(String country) {
    return (root, query, cb) -> {
        // root.join walks the @ManyToOne to Supplier
        Join<Product, Supplier> supplier = root.join("supplier");
        return cb.equal(supplier.get("country"), country);
    };
}
    • For a to-many join that can multiply rows, de-duplicate. Set distinct on the CriteriaQuery (the second lambda parameter), and guard against the count query (which has no ORDER BY and must not join needlessly):
    public static Specification<Product> hasTag(String tag) {
    return (root, query, cb) -> {
        query.distinct(true);                       // avoid duplicate products
        Join<Product, Tag> tags = root.join("tags", JoinType.INNER);
        return cb.equal(tags.get("name"), tag);
    };
}
    • Performance note: joining inside a Specification fixes the WHERE, but it does not fetch the association eagerly. To avoid N+1 when you read the joined data, use an @EntityGraph on the repository method or a separate fetch — see the pitfalls below.

    Step 8 — Sorting, Distinct, And the count() Query Gotcha#

    • You can sort inside a Specification, but prefer Pageable/Sort for the common case. When you do touch query, remember Spring runs your Specification twice for a paged call: once for data, once for count.
    public static Specification<Product> activeSortedByPrice() {
    return (root, query, cb) -> {
        // Guard: the count query's result type is Long, not Product.
        // Setting orderBy / fetch on it can break it — so only do so for the data query.
        if (Long.class != query.getResultType() && long.class != query.getResultType()) {
            query.orderBy(cb.desc(root.get("price")));
        }
        return cb.isTrue(root.get("active"));
    };
}
    • This getResultType() guard is the canonical way to make join-fetch / ordering Specifications safe for paging.

    Step 9 — Reusable, Generic Specifications#

    • Once you have a few, factor common patterns into a tiny generic helper so any entity can reuse them:
    public final class Specs {

    private Specs() { }

    public static <T> Specification<T> eq(String field, Object value) {
        return value == null ? null
                : (root, query, cb) -> cb.equal(root.get(field), value);
    }

    public static <T> Specification<T> like(String field, String value) {
        return (value == null || value.isBlank()) ? null
                : (root, query, cb) -> cb.like(
                        cb.lower(root.get(field)), "%" + value.toLowerCase() + "%");
    }

    public static <T> Specification<T> gte(String field, Comparable value) {
        return value == null ? null
                : (root, query, cb) -> cb.greaterThanOrEqualTo(root.get(field), value);
    }
}
    • Returning null for an absent value is the key idiom — Specification.where(...).and(null) is a no-op, so building a filter becomes a clean chain:
    Specification<Product> spec = Specification
        .where(Specs.<Product>eq("category", filter.category()))
        .and(Specs.like("name", filter.nameLike()))
        .and(Specs.gte("price", filter.minPrice()));

    Step 10 — Compile-Time Safety With The JPA Metamodel#

    • The string root.get("price") is not checked at compile time — a typo ("pirce") blows up only at runtime. The JPA static metamodel fixes this by generating a Product_ class with typed attribute references.
    • Add the Hibernate metamodel generator as an annotation processor:
    <dependency>
    <groupId>org.hibernate.orm</groupId>
    <artifactId>hibernate-jpamodelgen</artifactId>
    <scope>provided</scope>
</dependency>
    • After a build, reference attributes type-safely:
    public static Specification<Product> priceGreaterThan(BigDecimal min) {
    // Product_.price is generated, typed, and refactor-safe
    return (root, query, cb) -> cb.greaterThanOrEqualTo(root.get(Product_.price), min);
}
    • Now renaming the price field (or changing its type) becomes a compile error, not a production surprise.

    Step 11 — Test Specifications With Testcontainers#

    • Specifications are best tested against a real database (string paths and joins behave subtly differently across vendors). Use Testcontainers with Postgres (see Spring Boot 3.x JunitTest 5 for the testing foundation).
    @DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Testcontainers
class ProductSpecificationTest {

    @Container
    @ServiceConnection
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired
    private ProductRepository repository;

    @BeforeEach
    void seed() {
        repository.save(book("Clean Code", new BigDecimal("35"), true));
        repository.save(book("Old Manual", new BigDecimal("5"), false));
    }

    @Test
    void filtersByCategoryAndMinPrice() {
        var filter = new ProductFilter("BOOKS", new BigDecimal("20"), null, null, true);

        List<Product> result =
                repository.findAll(ProductSpecifications.fromFilter(filter));

        assertThat(result)
                .hasSize(1)
                .first()
                .extracting(Product::getName)
                .isEqualTo("Clean Code");
    }

    @Test
    void emptyFilterReturnsEverything() {
        var empty = new ProductFilter(null, null, null, null, null);

        assertThat(repository.findAll(ProductSpecifications.fromFilter(empty)))
                .hasSize(2);
    }
}

    Common Pitfalls#

    • Typos in root.get("..."). String paths are runtime-checked. Use the metamodel (Product_.price) for compile-time safety (Step 10).
    • Duplicate rows from to-many joins. A join on a @OneToMany/@ManyToMany multiplies rows. Call query.distinct(true) (Step 7).
    • Breaking the count query. Setting orderBy or a fetch join unconditionally breaks the paged count call. Guard with query.getResultType() (Step 8).
    • N+1 after filtering. A join filters but does not fetch. Reading the association lazily later triggers N+1. Use @EntityGraph on the repository method to fetch eagerly.
    • null vs empty predicate confusion. Returning null from a Specification means "always true". That is intentional for optional filters — but don't return null when you meant cb.isNull(path).
    • LIKE case sensitivity. Postgres LIKE is case-sensitive. Wrap both sides in cb.lower(...) or use ILIKE via a native fragment (Step 3).
    • Putting heavy logic in the lambda. The Specification runs at query-build time. Don't call the database or do I/O inside toPredicate.

    Best Practices#

    • Keep each predicate a small, named static factory (hasCategory, priceGreaterThan) — readable and unit-testable.
    • Build dynamic filters by collecting predicates into a list and cb.and(...)-ing them, or by returning null for absent filters and chaining .and().
    • Use the metamodel (hibernate-jpamodelgen) in any non-trivial codebase to kill string-path typos.
    • Reach for Specifications for dynamic queries only; keep fixed queries as derived methods or @Query.
    • Always page large result sets (findAll(spec, pageable)) and guard the count query when you order/fetch.
    • Add query.distinct(true) whenever a Specification joins a to-many association.
