    JPA With Postgres View Table#

    What Is The Topic#

    • A database view is a named, stored query that behaves like a read-only (or sometimes writable) table. It does not hold its own data — it computes its rows from one or more underlying tables every time you query it.
    • Views are a clean way to push joins, aggregations, filtering, and column shaping into the database, so your application can map a single, simple JPA entity to a complex result instead of writing the same query everywhere.
    • In Spring Boot 3 / Hibernate 6 you map a view exactly like a table — with an @Entity and @Table(name = "...") — but you treat it as read-only and adjust a few settings so Hibernate never tries to INSERT, UPDATE, or DELETE against it.
    • This note builds it step by step: a plain view, mapping it to an entity, querying it with a Spring Data repository, then materialized views, updatable views, DDL management with Flyway, and the common pitfalls.
    • See JPA In Spring Boot and Hibernate for the underlying ORM concepts this note assumes.

    Why Map A View Instead Of A Query#

    • It is fair to ask: if a view is just a query, why not run the query directly with JPQL or @Query? Views earn their place when:
    Reason What a view gives you
    Encapsulation The complex SQL (joins/aggregations) lives in one place in the DB, not scattered across the codebase.
    Reuse Many services, reports, and even other views can read the same shaped data.
    A stable contract The view is an API. You can refactor the underlying tables and keep the view's columns stable.
    Security Grant read access to a view that exposes only safe columns, without granting access to base tables.
    Performance A materialized view caches the computed result on disk and can be indexed.
    Clean mapping Your entity maps 1:1 to the view's columns — no @Formula, no DTO projection gymnastics.

    View vs Materialized View#

    • Postgres supports two kinds of views, and the difference drives how you map and refresh them:
    Aspect Regular VIEW MATERIALIZED VIEW
    Data stored? No — recomputed on every query. Yes — result is stored on disk.
    Freshness Always live (reflects base tables instantly). Stale until you REFRESH.
    Read cost Pays the query cost every time. Cheap reads (it is a real table on disk).
    Can be indexed? No (indexes live on the base tables). Yes — you can index it directly.
    Use when Data changes often and must be live. Expensive aggregation read far more often than the data changes.

    The Example Domain#

    • We will build a small reporting scenario. Two base tables — customers and orders — and a view customer_order_summary that aggregates each customer's order count and total spend.
    CREATE TABLE customers (
    id         BIGSERIAL PRIMARY KEY,
    name       VARCHAR(200) NOT NULL,
    country    VARCHAR(100) NOT NULL,
    created_at TIMESTAMP    NOT NULL DEFAULT now()
);

CREATE TABLE orders (
    id          BIGSERIAL PRIMARY KEY,
    customer_id BIGINT       NOT NULL REFERENCES customers (id),
    amount      NUMERIC(12,2) NOT NULL,
    status      VARCHAR(20)  NOT NULL,
    created_at  TIMESTAMP    NOT NULL DEFAULT now()
);

    Step 1 — Create The View In Postgres#

    • A view is created with CREATE VIEW ... AS <select>. Our summary joins the two tables, groups by customer, and computes aggregates. Note that every column the entity will map must have a stable, named column — alias computed columns explicitly.
    CREATE VIEW customer_order_summary AS
SELECT
    c.id                         AS customer_id,
    c.name                       AS customer_name,
    c.country                    AS country,
    COUNT(o.id)                  AS order_count,
    COALESCE(SUM(o.amount), 0)   AS total_spent,
    MAX(o.created_at)            AS last_order_at
FROM customers c
LEFT JOIN orders o
       ON o.customer_id = c.id
      AND o.status = 'COMPLETED'
GROUP BY c.id, c.name, c.country;
    • customer_id is unique per row — that matters, because every JPA entity needs an @Id, and the id column must uniquely identify a row in the view. A GROUP BY on the primary key guarantees this.
    • COALESCE(SUM(...), 0) turns a NULL sum (a customer with no orders) into 0, so the mapped Java field is never null.

    Step 2 — Map The View To A Read-Only Entity#

    • You map a view with the same annotations as a table — @Entity + @Table. The crucial additions make it read-only so Hibernate never emits write SQL against it:
    import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.Id;
import jakarta.persistence.Table;
import org.hibernate.annotations.Immutable;
import java.math.BigDecimal;
import java.time.LocalDateTime;

@Entity
@Table(name = "customer_order_summary")
@Immutable   // Hibernate: this entity is never updated — skip dirty checking
public class CustomerOrderSummary {

    @Id
    @Column(name = "customer_id")
    private Long customerId;

    @Column(name = "customer_name")
    private String customerName;

    @Column(name = "country")
    private String country;

    @Column(name = "order_count")
    private long orderCount;

    @Column(name = "total_spent")
    private BigDecimal totalSpent;

    @Column(name = "last_order_at")
    private LocalDateTime lastOrderAt;

    protected CustomerOrderSummary() { }   // JPA requires a no-arg constructor

    // getters only — no setters, this is read-only
    public Long getCustomerId()        { return customerId; }
    public String getCustomerName()    { return customerName; }
    public String getCountry()         { return country; }
    public long getOrderCount()        { return orderCount; }
    public BigDecimal getTotalSpent()  { return totalSpent; }
    public LocalDateTime getLastOrderAt() { return lastOrderAt; }
}
    • @org.hibernate.annotations.Immutable tells Hibernate the entity's state never changes, so it is excluded from dirty checking and flush — a real performance win and a safety net against accidental writes.
    • Map only the columns you need. The @Column(name = ...) must match the view's aliased column names from Step 1.
    • Use the correct Java types: Postgres NUMERIC → BigDecimal, TIMESTAMP → LocalDateTime, COUNT(...) → long.

    Step 3 — Stop Hibernate From Generating DDL For The View#

    • This is the most common mistake. If spring.jpa.hibernate.ddl-auto is update or create, Hibernate sees your @Entity and tries to CREATE TABLE customer_order_summary — which collides with the view, or worse, creates a real empty table.
    • A view is not managed by Hibernate's schema tooling. Turn DDL generation off and manage the view yourself (manually or, better, with Flyway — see Step 8):
    # application.properties
spring.datasource.url=jdbc:postgresql://localhost:5432/shop
spring.datasource.username=shop
spring.datasource.password=secret

# NEVER let Hibernate manage the schema when you use views.
spring.jpa.hibernate.ddl-auto=none

# Helpful while developing
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
    • ddl-auto=none is the right setting for any production app that owns its schema through migrations. Views make it mandatory.

    Step 4 — Create A Spring Data Repository#

    • Because the view is mapped as a normal entity, you get the full Spring Data repository for free — derived queries, paging, sorting, all of it. Just keep it read-only in spirit.
    import org.springframework.data.jpa.repository.JpaRepository;
import org.springframework.data.repository.query.Param;
import org.springframework.data.jpa.repository.Query;
import java.math.BigDecimal;
import java.util.List;

public interface CustomerOrderSummaryRepository
        extends JpaRepository<CustomerOrderSummary, Long> {

    // Derived query — Spring builds the WHERE clause from the method name
    List<CustomerOrderSummary> findByCountry(String country);

    // Derived query with ordering
    List<CustomerOrderSummary> findByOrderCountGreaterThanOrderByTotalSpentDesc(long minOrders);

    // Custom JPQL against the view entity
    @Query("""
           SELECT s FROM CustomerOrderSummary s
           WHERE s.totalSpent >= :threshold
           ORDER BY s.totalSpent DESC
           """)
    List<CustomerOrderSummary> findBigSpenders(@Param("threshold") BigDecimal threshold);
}
    • Calling save(), delete(), or any write method on this repository will make Hibernate try to write to the view and fail at the database level — @Immutable is your guard, but just don't expose write paths in your service layer.

    Step 5 — Query It From A Service#

    • Inject the repository and use it exactly like any other. The service stays clean because the heavy lifting lives in the view.
    import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import java.math.BigDecimal;
import java.util.List;

@Service
public class ReportingService {

    private final CustomerOrderSummaryRepository summaryRepository;

    public ReportingService(CustomerOrderSummaryRepository summaryRepository) {
        this.summaryRepository = summaryRepository;
    }

    // readOnly = true matches the nature of a view and lets Hibernate skip
    // flush/dirty-checking for the whole transaction.
    @Transactional(readOnly = true)
    public List<CustomerOrderSummary> topSpendersIn(String country, BigDecimal min) {
        return summaryRepository.findByCountry(country).stream()
                .filter(s -> s.getTotalSpent().compareTo(min) >= 0)
                .toList();
    }

    @Transactional(readOnly = true)
    public List<CustomerOrderSummary> bigSpenders(BigDecimal threshold) {
        return summaryRepository.findBigSpenders(threshold);
    }
}
    • @Transactional(readOnly = true) is the idiomatic pairing for view-backed queries: it signals intent, lets the JDBC driver/connection pool optimize, and ensures no accidental flush.

    Step 6 — Paging And Sorting Over A View#

    • Reports are usually paged. Since the view is a real entity, Pageable works out of the box — Spring wraps the view's SELECT in LIMIT/OFFSET and runs a COUNT query for the total.
    import org.springframework.data.domain.Page;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Sort;

@Transactional(readOnly = true)
public Page<CustomerOrderSummary> page(int page, int size) {
    Pageable pageable = PageRequest.of(page, size,
            Sort.by("totalSpent").descending());
    return summaryRepository.findAll(pageable);
}
    • Caveat: sorting/paging a non-materialized view re-runs the full underlying query on every page request. If the view is expensive, see Step 7 (materialized views).

    Step 7 — Materialized Views For Expensive Aggregations#

    • When the aggregation is costly and the data does not need to be live to the second, a materialized view stores the result on disk so reads are cheap, and you can index it.
    -- 1. Create it (the AS query is the same as before)
CREATE MATERIALIZED VIEW customer_order_summary_mv AS
SELECT
    c.id                       AS customer_id,
    c.name                     AS customer_name,
    c.country                  AS country,
    COUNT(o.id)                AS order_count,
    COALESCE(SUM(o.amount), 0) AS total_spent,
    MAX(o.created_at)          AS last_order_at
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'COMPLETED'
GROUP BY c.id, c.name, c.country;

-- 2. A UNIQUE index is REQUIRED for REFRESH ... CONCURRENTLY, and speeds up reads
CREATE UNIQUE INDEX ux_cos_mv_customer ON customer_order_summary_mv (customer_id);
CREATE INDEX ix_cos_mv_country         ON customer_order_summary_mv (country);
    • Mapping is identical — point @Table at the materialized view name. It is still @Immutable and read-only.
    • Refreshing: a materialized view is stale until refreshed. REFRESH MATERIALIZED VIEW CONCURRENTLY rebuilds it without locking out readers (it needs the unique index above):
    import org.springframework.stereotype.Repository;
import jakarta.persistence.EntityManager;
import jakarta.persistence.PersistenceContext;
import org.springframework.transaction.annotation.Transactional;

@Repository
public class MaterializedViewRefresher {

    @PersistenceContext
    private EntityManager entityManager;

    @Transactional   // a refresh is a write operation — needs a real transaction
    public void refreshCustomerOrderSummary() {
        entityManager
            .createNativeQuery("REFRESH MATERIALIZED VIEW CONCURRENTLY customer_order_summary_mv")
            .executeUpdate();
    }
}
    • Drive the refresh on a schedule with Spring's @Scheduled (enable it with @EnableScheduling):
    @Scheduled(fixedRateString = "PT15M")   // every 15 minutes
public void scheduledRefresh() {
    refresher.refreshCustomerOrderSummary();
}
    • CONCURRENTLY cannot run inside the same transaction as other DDL and cannot be used on the first refresh of a never-populated view — use a plain REFRESH once to populate, then CONCURRENTLY thereafter.

    Step 8 — Manage The View's DDL With Flyway#

    • Since Hibernate no longer creates the schema, something must. The clean answer is a migration tool like [[Flyway]] (or Liquibase) so the view definition is versioned alongside your code and applied automatically on startup.
    -- src/main/resources/db/migration/V2__customer_order_summary_view.sql
CREATE OR REPLACE VIEW customer_order_summary AS
SELECT
    c.id                       AS customer_id,
    c.name                     AS customer_name,
    c.country                  AS country,
    COUNT(o.id)                AS order_count,
    COALESCE(SUM(o.amount), 0) AS total_spent,
    MAX(o.created_at)          AS last_order_at
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id AND o.status = 'COMPLETED'
GROUP BY c.id, c.name, c.country;

    <dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
    • CREATE OR REPLACE VIEW makes the migration re-runnable in spirit and lets you evolve the view (you can add columns at the end; you cannot remove/rename existing ones with REPLACE — use DROP VIEW + CREATE in a new migration for that).
    • This is the production-correct setup: ddl-auto=none + Flyway owns every table, view, and index.

    Step 9 — Updatable Views (When You Need To Write)#

    • A simple Postgres view (selecting from one table, no aggregation/join/DISTINCT/GROUP BY) is automatically updatable — you can INSERT/UPDATE/DELETE through it. For complex views, you make them writable with an INSTEAD OF trigger.
    • If you genuinely map an updatable view, drop @Immutable and add setters so Hibernate can write through it:
    -- A simple, automatically-updatable view exposing a subset of columns
CREATE VIEW active_customers AS
SELECT id, name, country, created_at
FROM customers
WHERE country IS NOT NULL;

    @Entity
@Table(name = "active_customers")
// NOTE: no @Immutable here — writes through this view are allowed
public class ActiveCustomer {
    @Id private Long id;
    private String name;
    private String country;
    // getters + setters ...
}
    • Recommendation: keep views read-only by default. Reach for updatable views only when the view is a thin, single-table projection — otherwise the write semantics get subtle fast and an INSTEAD OF trigger is clearer than relying on auto-updatability.

    Step 10 — Test The Mapping With Testcontainers#

    • Views are a Postgres feature, so an H2 in-memory test will not exercise them faithfully. Use Testcontainers with a real Postgres image (see also Spring Boot 3.x JunitTest 5 for the testing foundations).
    import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.autoconfigure.jdbc.AutoConfigureTestDatabase;
import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.testcontainers.containers.PostgreSQLContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

import java.util.List;

import static org.assertj.core.api.Assertions.assertThat;

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)
@Testcontainers
class CustomerOrderSummaryRepositoryTest {

    @Container
    @ServiceConnection   // Spring Boot 3.1+ wires the datasource automatically
    static PostgreSQLContainer<?> postgres =
            new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired
    private CustomerOrderSummaryRepository repository;

    @Test
    void mapsViewRowsToEntities() {
        // Flyway runs migrations (tables + view + seed data) before the test
        List<CustomerOrderSummary> all = repository.findAll();

        assertThat(all).isNotEmpty();
        assertThat(all)
            .allSatisfy(s -> assertThat(s.getCustomerId()).isNotNull())
            .anySatisfy(s -> assertThat(s.getOrderCount()).isGreaterThan(0));
    }
}
    • Let Flyway run inside the test so the container gets the exact same tables, views, and indexes as production. Seed rows with a V999__test_seed.sql migration (or an @Sql script) so the view has data to aggregate.

    Common Pitfalls#

    • ddl-auto is not none. Hibernate tries to create a table over your view. This is the #1 cause of "the view isn't there / it's empty." → set it to none and use Flyway (Step 3, Step 8).
    • No usable @Id. Every entity needs a unique id column. If your view has no naturally unique column, build one (row_number() is fragile) or use a composite @IdClass/@EmbeddedId over the real key columns.
    • Writing through a non-updatable view. A save() on an aggregated view throws at the DB. Keep it @Immutable and read-only (Step 2).
    • Forgetting to refresh a materialized view. Reads silently return stale data. Schedule a refresh and document the staleness window (Step 7).
    • REFRESH ... CONCURRENTLY without a unique index. Postgres rejects it. Always create the unique index first (Step 7).
    • null from aggregates. SUM/MAX over zero rows is NULL. Wrap with COALESCE or map the field as a nullable wrapper type (Step 1).
    • Testing on H2. H2's view/materialized-view support differs from Postgres. Test against real Postgres with Testcontainers (Step 10).

    Best Practices#

    • Always mark view entities @Immutable and query them under @Transactional(readOnly = true).
    • Manage every view through Flyway/Liquibase migrations; never let Hibernate generate the schema (ddl-auto=none).
    • Prefer a regular view for live data; switch to a materialized view only when reads vastly outnumber base-table changes and you need indexing.
    • Alias every computed column in the view, and COALESCE aggregates that can be null.
    • Map only the columns you need — a view entity is a read model, not your domain aggregate.
    • Keep view-backed read models in a separate package (e.g. reporting) to signal they are queries, not write-side entities.
