    Spring Data MongoDB#

    What Is The Topic#

    • MongoDB is a document-oriented NoSQL database: it stores BSON documents (binary JSON) inside collections, with a flexible schema instead of rigid tables and rows.
    • Spring Data MongoDB brings the familiar Spring Data programming model — @Document mapping, MongoRepository, derived query methods, and a powerful MongoTemplate — to MongoDB, so you work with Java objects and let the framework handle serialization and queries.
    • In Spring Boot 3 / Java 17+ everything is auto-configured: add the starter, point it at a database, and you get a ready-to-use MongoTemplate and repository support.
    • This note builds it step by step: connection, document mapping, repositories, derived & @Query methods, the MongoTemplate and Criteria API, the aggregation pipeline, indexing, embedding vs referencing, transactions, and testing with Testcontainers.
    • See JPA In Spring Boot for the relational counterpart — the mental models overlap but the data model is very different (documents, not joins).

    SQL vs MongoDB — The Mental Model Shift#

    • If you come from JPA, remap your vocabulary before writing code. MongoDB favors embedding related data into one document over normalizing across tables.
    Relational (JPA) MongoDB
    Table Collection
    Row Document (BSON)
    Column Field
    Primary key _id (an ObjectId by default)
    Join Embed the data, or reference + look up
    Schema enforced by DDL Schema-flexible (enforced by your app/validation)
    @Entity / @Table @Document
    JpaRepository MongoRepository

    Step 1 — Add The Dependency And Connect#

    • Add the reactive-free starter (blocking/imperative model, which this note uses):
    <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-mongodb</artifactId>
</dependency>
    • Point Spring Boot at your database. The single uri property is the cleanest way (it carries host, port, database, credentials, and options):
    # application.properties
spring.data.mongodb.uri=mongodb://app_user:secret@localhost:27017/shop?authSource=admin

# Helpful in development — log the queries Spring Data issues
logging.level.org.springframework.data.mongodb.core.MongoTemplate=DEBUG
    • Spin up a local MongoDB quickly with Docker:
    docker run -d --name mongo -p 27017:27017 \
  -e MONGO_INITDB_ROOT_USERNAME=root \
  -e MONGO_INITDB_ROOT_PASSWORD=secret \
  mongo:7

    Step 2 — Map A Document#

    • A document class is annotated with @Document. Each instance becomes one BSON document in the collection.
    import org.springframework.data.annotation.Id;
import org.springframework.data.mongodb.core.mapping.Document;
import org.springframework.data.mongodb.core.mapping.Field;
import org.springframework.data.mongodb.core.index.Indexed;
import java.math.BigDecimal;
import java.time.Instant;
import java.util.List;

@Document(collection = "products")
public class Product {

    @Id
    private String id;                  // maps to _id; String holds the ObjectId

    private String name;

    @Indexed                            // create a single-field index on category
    private String category;

    private BigDecimal price;

    private boolean active;

    @Field("released_on")               // store under a different BSON field name
    private Instant releasedOn;

    private List<String> tags;          // arrays map naturally to BSON arrays

    private Address warehouse;          // embedded sub-document (a POJO, no @Document needed)

    // constructors / getters / setters omitted
}

    public class Address {                  // plain POJO — embedded inside Product
    private String city;
    private String country;
    // getters / setters
}
    Annotation Purpose
    @Document(collection = "...") Marks the class; sets the collection name.
    @Id Maps the field to _id. Use String (auto ObjectId) or your own key.
    @Field("name") Stores under a custom BSON field name.
    @Indexed Creates an index on that field.
    @DBRef / @DocumentReference Reference another document (see Step 9).
    @Version Optimistic locking.

    Step 3 — Create A Repository#

    • Extend MongoRepository<T, ID> for instant CRUD, paging, and sorting — no implementation needed.
    import org.springframework.data.mongodb.repository.MongoRepository;

public interface ProductRepository extends MongoRepository<Product, String> {
}

    @Service
public class ProductService {

    private final ProductRepository repository;

    public ProductService(ProductRepository repository) {
        this.repository = repository;
    }

    public Product create(Product p) {
        return repository.save(p);          // insert or replace by _id
    }

    public Optional<Product> byId(String id) {
        return repository.findById(id);
    }

    public List<Product> all() {
        return repository.findAll();
    }
}

    Step 4 — Derived Query Methods#

    • As with JPA, Spring Data parses method names into MongoDB queries. The same keywords apply (And, Or, Between, LessThan, Like, In, OrderBy, IgnoreCase…).
    public interface ProductRepository extends MongoRepository<Product, String> {

    List<Product> findByCategory(String category);

    List<Product> findByCategoryAndActiveTrue(String category);

    List<Product> findByPriceBetween(BigDecimal min, BigDecimal max);

    List<Product> findByNameContainingIgnoreCase(String text);

    List<Product> findByTagsContaining(String tag);           // matches an array element

    Page<Product> findByCategory(String category, Pageable pageable);

    long countByActiveTrue();

    boolean existsByName(String name);
}
    • findByTagsContaining("sale") matches documents where the tags array contains "sale" — array querying is a natural fit for the document model.

    Step 5 — Custom Queries With @Query#

    • When a derived name gets unwieldy, write the raw MongoDB query (JSON filter) with @Query. Placeholders ?0, ?1… bind method parameters.
    public interface ProductRepository extends MongoRepository<Product, String> {

    // Raw MongoDB filter document
    @Query("{ 'category': ?0, 'price': { $gte: ?1 } }")
    List<Product> search(String category, BigDecimal minPrice);

    // Projection: return only selected fields (second JSON = field selection)
    @Query(value = "{ 'active': true }", fields = "{ 'name': 1, 'price': 1 }")
    List<Product> findActiveNamesAndPrices();

    // Delete query
    @Query(delete = true, value = "{ 'active': false }")
    long deleteInactive();
}
    • The fields attribute is a projection — 1 includes a field, 0 excludes it — to fetch lighter documents over the wire.

    Step 6 — MongoTemplate And The Criteria API#

    • MongoRepository covers most needs, but MongoTemplate is the lower-level, programmatic API for dynamic queries, partial updates, and aggregations. Build filters fluently with Criteria.
    import org.springframework.data.mongodb.core.MongoTemplate;
import org.springframework.data.mongodb.core.query.Criteria;
import org.springframework.data.mongodb.core.query.Query;
import org.springframework.data.mongodb.core.query.Update;

@Repository
public class ProductQueryRepository {

    private final MongoTemplate mongoTemplate;

    public ProductQueryRepository(MongoTemplate mongoTemplate) {
        this.mongoTemplate = mongoTemplate;
    }

    // Dynamic filtering — append only the criteria that are present
    public List<Product> search(String category, BigDecimal minPrice, Boolean activeOnly) {
        Query query = new Query();

        if (category != null)
            query.addCriteria(Criteria.where("category").is(category));
        if (minPrice != null)
            query.addCriteria(Criteria.where("price").gte(minPrice));
        if (Boolean.TRUE.equals(activeOnly))
            query.addCriteria(Criteria.where("active").is(true));

        return mongoTemplate.find(query, Product.class);
    }

    // Partial, atomic update — change ONE field without loading the document
    public void deactivate(String id) {
        Query q = new Query(Criteria.where("_id").is(id));
        Update u = new Update().set("active", false);
        mongoTemplate.updateFirst(q, u, Product.class);
    }

    // Atomic increment + push to an array in a single round-trip
    public void addTagAndBumpViews(String id, String tag) {
        Query q = new Query(Criteria.where("_id").is(id));
        Update u = new Update().push("tags", tag).inc("views", 1);
        mongoTemplate.updateFirst(q, u, Product.class);
    }
}
    • Why Update matters: repository.save() rewrites the whole document. MongoTemplate + Update lets you change one field atomically ($set, $inc, $push, $pull) — safer under concurrency and cheaper on the wire.

    Step 7 — The Aggregation Pipeline#

    • MongoDB's aggregation pipeline is its analytics engine — a sequence of stages ($match, $group, $sort, $project…) that transform documents. Spring Data wraps it in a type-safe builder.
    import org.springframework.data.mongodb.core.aggregation.Aggregation;
import org.springframework.data.mongodb.core.aggregation.AggregationResults;
import static org.springframework.data.mongodb.core.aggregation.Aggregation.*;

public List<CategorySales> salesByCategory() {
    Aggregation aggregation = newAggregation(
            match(Criteria.where("active").is(true)),     // $match: filter first
            group("category")                              // $group: by category
                    .count().as("productCount")
                    .sum("price").as("totalValue")
                    .avg("price").as("averagePrice"),
            sort(Sort.Direction.DESC, "totalValue"),       // $sort
            project("productCount", "totalValue", "averagePrice")
                    .and("_id").as("category")             // rename the group key
    );

    AggregationResults<CategorySales> results =
            mongoTemplate.aggregate(aggregation, "products", CategorySales.class);

    return results.getMappedResults();
}

    // Target POJO for the aggregation output
public record CategorySales(String category, long productCount,
                            BigDecimal totalValue, BigDecimal averagePrice) { }
    • The pipeline runs inside the database, so aggregation is fast and avoids pulling raw documents into the JVM. Put $match first so later stages process fewer documents.

    Step 8 — Indexing For Performance#

    • Without an index, MongoDB does a collection scan. Index the fields you filter and sort on. Declare them on the document for simple cases, or programmatically for compound indexes.
    import org.springframework.data.mongodb.core.index.CompoundIndex;
import org.springframework.data.mongodb.core.index.CompoundIndexes;

@Document("products")
@CompoundIndexes({
    // A compound index supporting "find active products in a category, sorted by price"
    @CompoundIndex(name = "cat_active_price_idx",
                   def = "{ 'category': 1, 'active': 1, 'price': -1 }")
})
public class Product { /* ... */ }
    • Auto-index creation is OFF by default in Spring Boot (for safety/performance). Enable it explicitly in development, but create indexes deliberately (e.g. via migrations) in production:
    spring.data.mongodb.auto-index-creation=true
    • A unique index enforces uniqueness at the DB level:
    @Indexed(unique = true)
private String sku;

    Step 9 — Embedding vs Referencing (Modeling Relationships)#

    • MongoDB has no joins in the relational sense. You model relationships two ways, and choosing well is the core skill of document design:
    Strategy Use when How
    Embed (sub-document) The child belongs to one parent, is read together, and is bounded in size (e.g. an address, order lines). Plain POJO field — stored inline in the same document.
    Reference The child is large, shared, or grows unbounded (e.g. a user referenced by many orders). @DocumentReference storing the related _id; resolved with a lookup. 
    @Document("orders")
public class Order {
    @Id private String id;

    private List<OrderLine> lines;       // EMBED: read with the order, bounded

    @DocumentReference                   // REFERENCE: store the customer's _id
    private Customer customer;
}
    • Default to embedding — it is the document model's strength (one read, no join). Reference only when sharing or unbounded growth forces it.
    • Prefer @DocumentReference over the older @DBRef: it stores a plain id (not a DB-coupled pointer), is more flexible, and is the current recommendation.

    Step 10 — Transactions (Multi-Document)#

    • Single-document writes in MongoDB are always atomic — and good document design means most operations touch one document. When you genuinely must update multiple documents atomically, MongoDB supports multi-document transactions (requires a replica set; a standalone server does not support them).
    import org.springframework.transaction.annotation.Transactional;

@Service
public class OrderService {

    private final ProductRepository products;
    private final OrderRepository orders;

    // Both writes commit together or roll back together
    @Transactional
    public Order placeOrder(Order order, String productId) {
        productQueryRepository.deactivate(productId);   // update one collection
        return orders.save(order);                      // insert into another
    }
}
    • Spring auto-configures a MongoTransactionManager when it detects you need one (or define it as a @Bean). Keep transactions short — they hold resources on the server.

    Step 11 — Test With Testcontainers#

    • Use a real MongoDB in tests via Testcontainers rather than an embedded fake — query and aggregation behavior must match production (see Spring Boot 3.x JunitTest 5 for the testing foundation).
    import org.springframework.boot.test.autoconfigure.data.mongo.DataMongoTest;
import org.springframework.boot.testcontainers.service.connection.ServiceConnection;
import org.testcontainers.containers.MongoDBContainer;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;

@DataMongoTest
@Testcontainers
class ProductRepositoryTest {

    @Container
    @ServiceConnection                          // wires spring.data.mongodb.uri automatically
    static MongoDBContainer mongo = new MongoDBContainer("mongo:7");

    @Autowired
    private ProductRepository repository;

    @Test
    void savesAndQueriesByCategory() {
        repository.save(product("Clean Code", "BOOKS", new BigDecimal("35"), true));
        repository.save(product("Old Manual", "BOOKS", new BigDecimal("5"), false));

        List<Product> active = repository.findByCategoryAndActiveTrue("BOOKS");

        assertThat(active)
                .hasSize(1)
                .first()
                .extracting(Product::getName)
                .isEqualTo("Clean Code");
    }
}
    • @DataMongoTest is the MongoDB test slice — it loads only the mapping + repository infrastructure, not the whole application, so tests start fast.

    Common Pitfalls#

    • save() overwrites the whole document. For a single-field change use MongoTemplate + Update ($set) to avoid lost updates and wasted bandwidth (Step 6).
    • Missing indexes → collection scans. Auto-index creation is off by default. Index your filter/sort fields deliberately (Step 8).
    • Over-referencing. Forcing relational habits (everything @DocumentReferenced) gives you N lookups and no joins. Prefer embedding (Step 9).
    • Unbounded embedded arrays. Embedding a list that grows forever can blow the 16 MB document limit. Reference instead (Step 9).
    • Transactions on a standalone server. Multi-document transactions need a replica set; they fail on a single standalone node (Step 10).
    • BigDecimal precision. Older drivers stored BigDecimal as a string/double; the modern driver maps it to BSON Decimal128 — verify your values round-trip exactly.
    • Testing on a fake. Embedded in-memory Mongo substitutes drift from real server behavior (especially aggregation). Use Testcontainers (Step 11).

    Best Practices#

    • Model around your queries. Design documents for how they are read, embedding what is read together.
    • Use MongoRepository for CRUD and derived queries; drop to MongoTemplate for dynamic filters, partial updates, and aggregations.
    • Prefer partial atomic updates (Update operators) over save() for concurrent writes.
    • Create indexes deliberately (compound, unique) and keep auto-index-creation off in production.
    • Default to embedding; reference only for shared or unbounded data, using @DocumentReference.
    • Run the aggregation pipeline in the database with $match first; map results into records/DTOs.
    • Test against real MongoDB with Testcontainers and the @DataMongoTest slice.
