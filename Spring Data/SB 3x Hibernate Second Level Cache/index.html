    Hibernate Second Level Cache In Spring Boot 3.x#

    What Is The Topic#

    • The second-level cache (2LC) is a SessionFactory-scoped cache that stores entity, collection, and (optionally) query data across transactions and across sessions. It sits between your application and the database to avoid repeated SQL reads of data that rarely changes.
    • This sharply contrasts with the first-level cache, which is the EntityManager / Session (the Persistence Context) — it lives only for one transaction and is always on.
    • In Spring Boot 3 / Hibernate 6 the recommended way to wire a 2LC is via the JCache (JSR-107) bridge with EhCache 3 as the provider. This note builds it step by step and then covers concurrency strategies, query/collection caching, verification, and the common pitfalls.
    • See Hibernate and JPA In Spring Boot for the underlying ORM concepts this note assumes.

    First-Level vs Second-Level Cache#

    • Knowing the difference is essential — most "the cache isn't working" confusion comes from mixing them up.
    Aspect First-Level Cache (L1) Second-Level Cache (L2)
    Scope One EntityManager / Session (one transaction). The whole SessionFactory (the application).
    Lifetime Cleared when the session/transaction ends. Lives until evicted/expired; survives transactions.
    Enabled by Always on, cannot be disabled. Opt-in — must be configured + entities annotated.
    Shared between users? No — private to one unit of work. Yes — shared across all sessions/threads.
    Stores Managed entities of the current session. Entity/collection data, natural-ids, query results.

    How The Second-Level Cache Is Structured#

    • Hibernate's 2LC is divided into independent regions, each with its own configuration:
    Region type What it stores Enabled by
    Entity region An entity's state by id (a dehydrated array of values, not the object). @Cache on the entity.
    Collection region The ids of a @OneToMany / @ManyToMany association. @Cache on the collection field.
    Query region Result-set ids for a specific query + parameters. Query cache enabled + setCacheable(true).
    Natural-id region Mapping from a @NaturalId to the primary key. @NaturalId + entity cached.
    • Important: the entity cache stores the disassembled state (a tuple of column values), not your Java object. On a hit, Hibernate rehydrates a fresh entity instance from that state — so two sessions never share the same object reference.

    Cache Concurrency Strategies#

    • When you cache an entity you must choose how concurrent reads/writes are coordinated. Pick the weakest strategy that is still correct for your data — stronger strategies cost more.
    Strategy Use when Behavior
    READ_ONLY Reference data that never changes after insert (countries, currencies). Fastest. Modifying a cached entity throws an exception.
    NONSTRICT_READ_WRITE Data that changes rarely and where a brief stale read is acceptable. On update, the entry is evicted (not updated). Small race window.
    READ_WRITE Data that changes and must stay consistent. Uses soft locks + versioning to keep the cache in sync. Most common for mutable entities.
    TRANSACTIONAL Full XA/JTA transactional consistency. Requires a JTA environment + a transactional cache provider. Rarely needed.

    Step 1 — Add The Dependencies#

    • For Spring Boot 3 / Hibernate 6 you need the Hibernate↔JCache bridge, the JCache API, and EhCache 3 with the jakarta classifier (the plain artifact still targets javax and will not work under Jakarta EE 9+):
    <!-- Hibernate's JCache (JSR-107) region factory -->
<dependency>
    <groupId>org.hibernate.orm</groupId>
    <artifactId>hibernate-jcache</artifactId>
</dependency>

<!-- JCache API (JSR-107) -->
<dependency>
    <groupId>javax.cache</groupId>
    <artifactId>cache-api</artifactId>
</dependency>

<!-- EhCache 3 as the actual cache provider — note the jakarta classifier -->
<dependency>
    <groupId>org.ehcache</groupId>
    <artifactId>ehcache</artifactId>
    <version>3.10.8</version>
    <classifier>jakarta</classifier>
</dependency>

    Why jakarta classifier? EhCache 3.10 ships two builds. The default uses javax.cache/javax.*; the jakarta-classified jar is compiled against the Jakarta namespace that Spring Boot 3 / Hibernate 6 use. Forgetting it leads to ClassNotFoundException / no-provider errors at startup.

    Step 2 — Enable The Cache In Configuration#

    • Turn the 2LC on and point Hibernate at the JCache provider in application.properties (or .yml). These are passed through as native Hibernate properties under spring.jpa.properties.*:
    # 1. switch on the second-level cache
spring.jpa.properties.hibernate.cache.use_second_level_cache=true

# 2. use the JCache region factory (shorthand 'jcache' works in Hibernate 6)
spring.jpa.properties.hibernate.cache.region.factory_class=jcache

# 3. tell JCache which provider to use (EhCache 3)
spring.jpa.properties.hibernate.javax.cache.provider=org.ehcache.jsr107.EhcacheCachingProvider

# 4. point at the EhCache config file (optional but recommended)
spring.jpa.properties.hibernate.javax.cache.uri=classpath:ehcache.xml

# 5. (dev only) emit statistics so we can verify hits/misses — see Step 6
spring.jpa.properties.hibernate.generate_statistics=true

# only cache entities explicitly marked @Cacheable (this is the default)
spring.jpa.properties.jakarta.persistence.sharedCache.mode=ENABLE_SELECTIVE
    • Note the namespaces: the cache enable flag is hibernate.cache.*, but the JCache provider/uri properties are hibernate.javax.cache.*. JSR-107 (javax.cache) kept the javax prefix even in the Jakarta era, so this is correct — do not "fix" it to jakarta.

    Step 3 — Mark Entities As Cacheable#

    • An entity is cached only if you annotate it. You need both:
      • @jakarta.persistence.Cacheable (the JPA standard marker, honored by ENABLE_SELECTIVE), and
      • @org.hibernate.annotations.Cache (the Hibernate annotation that picks the concurrency strategy).
    // Product.java
package com.example.demo.product;

import jakarta.persistence.*;
import org.hibernate.annotations.Cache;
import org.hibernate.annotations.CacheConcurrencyStrategy;

import java.math.BigDecimal;

@Entity
@Table(name = "products")
@Cacheable                                                   // JPA: include in 2LC
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)          // Hibernate: how to sync
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String name;
    private BigDecimal price;

    protected Product() { }

    public Product(String name, BigDecimal price) {
        this.name = name;
        this.price = price;
    }

    // getters / setters omitted
}
    • With this in place, the second time you findById the same product (in a new transaction) Hibernate serves it from the cache — no SELECT is issued.

    Step 4 — Configure The EhCache Regions#

    • Create src/main/resources/ehcache.xml (EhCache 3 / JSR-107 format). The cache alias must equal the region name, which by default is the fully-qualified entity class name:
    <config
    xmlns='http://www.ehcache.org/v3'
    xmlns:jsr107='http://www.ehcache.org/v3/jsr107'>

    <cache alias="com.example.demo.product.Product">
        <expiry>
            <ttl unit="seconds">3600</ttl>      <!-- live 1 hour -->
        </expiry>
        <heap unit="entries">1000</heap>         <!-- max 1000 entries on-heap -->
    </cache>

    <!-- region for the query cache (see Step 7) -->
    <cache alias="default-query-results-region">
        <expiry><ttl unit="seconds">300</ttl></expiry>
        <heap unit="entries">500</heap>
    </cache>

    <!-- internal region Hibernate uses to invalidate query results on writes -->
    <cache alias="default-update-timestamps-region">
        <expiry><none/></expiry>                 <!-- must never expire -->
        <heap unit="entries">5000</heap>
    </cache>
</config>
    • Tips:
      • If you omit a <cache> for a region, EhCache 3 (strict JSR-107) will complain about an unknown cache. You can change the region name with @Cache(region = "products") to use a shorter alias.
      • default-update-timestamps-region must have no expiry — it tracks table write times and is what keeps the query cache correct.

    Step 5 — Collection Caching#

    • Caching an entity does not cache its associations. To cache a @OneToMany/@ManyToMany, annotate the collection field too. The collection region stores only the child ids, so the children themselves must also be @Cacheable to fully avoid SQL.
    @Entity
@Cacheable
@Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class Category {

    @Id @GeneratedValue
    private Long id;

    @OneToMany(mappedBy = "category")
    @Cache(usage = CacheConcurrencyStrategy.READ_WRITE)   // cache the association
    private List<Product> products = new ArrayList<>();
}
    • Add a matching <cache> alias for the collection region — its name is FQCN.fieldName, e.g. com.example.demo.product.Category.products.

    Step 6 — Verify It Actually Works#

    • "Is my cache working?" should always be answered with evidence, not assumptions. Two reliable ways:

    • (a) Watch the SQL. Enable SQL logging and confirm the second read issues no SELECT:

    spring.jpa.show-sql=true
logging.level.org.hibernate.SQL=DEBUG
    • (b) Read the statistics. With hibernate.generate_statistics=true you can assert on hit/miss counts:
    import org.hibernate.SessionFactory;
import org.hibernate.stat.Statistics;
import jakarta.persistence.EntityManagerFactory;

Statistics stats = entityManagerFactory
        .unwrap(SessionFactory.class)
        .getStatistics();

long hits   = stats.getSecondLevelCacheHitCount();
long misses = stats.getSecondLevelCacheMissCount();
long puts   = stats.getSecondLevelCachePutCount();
// first findById -> miss + put ; second findById -> hit
    • A typical demonstration (each findById in its own transaction so L1 doesn't mask the result):
    -- 1st call: cache miss, SQL runs, entry put into 2LC
Hibernate: select p1_0.id, p1_0.name, p1_0.price from products p1_0 where p1_0.id=?
-- 2nd call: cache HIT, no SQL at all
secondLevelCacheHitCount = 1
    • Gotcha: if you call findById twice inside the same transaction, the second hit comes from the first-level cache and the 2LC counters won't move. Always test across separate transactions.

    Step 7 — The Query Cache (Use With Care)#

    • The entity cache only helps findById / getReference. To cache the results of a JPQL/Criteria query, you must enable the query cache and mark each query cacheable.
    spring.jpa.properties.hibernate.cache.use_query_cache=true

    // Spring Data JPA — opt a query into the cache via a QueryHint
import jakarta.persistence.QueryHint;
import org.springframework.data.jpa.repository.QueryHints;

public interface ProductRepository extends JpaRepository<Product, Long> {

    @QueryHints(@QueryHint(name = "org.hibernate.cacheable", value = "true"))
    List<Product> findByPriceLessThan(BigDecimal price);
}
    • How it works & why to be cautious:
      • The query cache stores only the ids of matching rows, then loads each entity from the entity cache — so the entity must also be @Cacheable, otherwise you trade one query for N selects.
      • The cache for a query is invalidated whenever any table it touches is modified (tracked via default-update-timestamps-region). On write-heavy tables it is constantly invalidated and can hurt performance.
      • Rule of thumb: use the query cache only for queries that run very often over rarely-changing tables.

    Step 8 — Cache Modes & Eviction At Runtime#

    • You can override caching behavior per-operation with CacheMode / CacheRetrieveMode / CacheStoreMode:
    Mode Meaning
    CacheStoreMode.USE Read and write the cache (default).
    CacheStoreMode.REFRESH Read DB, refresh the cache entry.
    CacheRetrieveMode.BYPASS Ignore the cache for reads (still writes). 
    // force a fresh DB read while still updating the cache
entityManager.find(Product.class, 1L,
    Map.of("jakarta.persistence.cache.retrieveMode", CacheRetrieveMode.BYPASS));
    • Programmatic eviction via the JPA Cache API:
    entityManagerFactory.getCache().evict(Product.class, 1L); // one entity
entityManagerFactory.getCache().evict(Product.class);     // whole region
entityManagerFactory.getCache().evictAll();               // everything

    Step 9 — Automatically Clearing The Cache On A Time Interval#

    • You usually don't want cached data to live forever — stale entries should be evicted automatically after a configurable period (e.g. every 5 minutes). There are two complementary mechanisms; prefer the first.

    Option A (recommended) — Declarative expiry in ehcache.xml#

    • EhCache 3 evicts entries automatically based on expiry policies you declare per region. Two policies:
    Policy Meaning Use for
    TTL (<ttl>, time-to-live) Evict an entry N time after it was written, regardless of how often it's read. Hard freshness guarantee — "never serve data older than 5 min".
    TTI (<tti>, time-to-idle) Evict an entry N time after it was last accessed. Each read resets the timer. Keep hot entries, drop idle ones.
    • A region that fully refreshes every 5 minutes uses a 5-minute TTL:
    <config xmlns='http://www.ehcache.org/v3'>

    <cache alias="com.example.demo.product.Product">
        <expiry>
            <ttl unit="minutes">5</ttl>      <!-- auto-evict 5 min after write -->
        </expiry>
        <heap unit="entries">1000</heap>
    </cache>

    <!-- Example combining idle + absolute lifetime is NOT allowed:
         EhCache 3 accepts exactly ONE of <ttl>, <tti>, <none>, or a custom class. -->
    <cache alias="com.example.demo.product.Category">
        <expiry>
            <tti unit="minutes">5</tti>      <!-- evict 5 min after last access -->
        </expiry>
        <heap unit="entries">500</heap>
    </cache>

</config>
    • Notes:
      • unit accepts seconds, minutes, hours, etc. So "5 minutes" is <ttl unit="minutes">5</ttl> (equivalently <ttl unit="seconds">300</ttl>).
      • Expiry is lazy: EhCache marks an entry expired by its timestamp and removes it on the next access or during background maintenance — there is no precise "clear at exactly 5:00.000". For a 2LC this lazy behavior is exactly what you want (no scheduler overhead).
      • You can set a default expiry for all caches with a <cache-template> and reference it via uses-template, so you don't repeat the policy per region.

    Make the interval configurable without editing XML#

    • Hard-coding 5 in ehcache.xml means a redeploy to change it. To drive the TTL from a Spring property, build the EhCache config programmatically and read the duration from application.properties:
    # application.properties
app.cache.product.ttl=5m        # Spring parses ISO-ish durations: 5m, 30s, 1h

    // CacheConfig.java — programmatic JCache config so the TTL comes from a property
package com.example.demo.config;

import com.example.demo.product.Product;
import org.ehcache.config.builders.*;
import org.ehcache.expiry.ExpiryPolicyBuilder;
import org.ehcache.jsr107.EhcacheCachingProvider;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.boot.autoconfigure.orm.jpa.HibernatePropertiesCustomizer;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

import javax.cache.CacheManager;
import javax.cache.Caching;
import java.time.Duration;
import java.util.Map;

@Configuration
public class CacheConfig {

    @Value("${app.cache.product.ttl:5m}")
    private Duration productTtl;          // injected as java.time.Duration

    @Bean
    public HibernatePropertiesCustomizer hibernatePropertiesCustomizer(CacheManager cacheManager) {
        // hand Hibernate the JCache manager we configured below
        return props -> props.put("hibernate.javax.cache.cache_manager", cacheManager);
    }

    @Bean
    public CacheManager jCacheManager() {
        EhcacheCachingProvider provider =
                (EhcacheCachingProvider) Caching.getCachingProvider(
                        EhcacheCachingProvider.class.getName());

        var ehcacheConfig = org.ehcache.config.builders.CacheManagerBuilder
                .newCacheManagerBuilder()
                .withCache(Product.class.getName(),                       // region == FQCN
                        CacheConfigurationBuilder.newCacheConfigurationBuilder(
                                Object.class, Object.class,               // Hibernate uses opaque keys/values
                                ResourcePoolsBuilder.heap(1000))
                            .withExpiry(ExpiryPolicyBuilder
                                .timeToLiveExpiration(productTtl))        // <-- TTL from the property
                            .build())
                .build(true);

        return provider.getCacheManager(provider.getDefaultURI(),
                ehcacheConfig.getRuntimeConfiguration().getClass().getClassLoader());
    }
}
    • Now changing app.cache.product.ttl to 10m (or via an env var / config server) re-tunes eviction without touching XML or code.

    Option B — Scheduled full flush with @Scheduled#

    • Sometimes you want to wipe the whole cache on a fixed cadence (e.g. a nightly reset, or to force a refresh every 5 minutes regardless of per-entry timestamps). Use Spring's scheduler to call the JPA Cache eviction API:
    // CacheEvictionScheduler.java
package com.example.demo.config;

import jakarta.persistence.EntityManagerFactory;
import lombok.extern.slf4j.Slf4j;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

@Slf4j
@Component
public class CacheEvictionScheduler {

    private final EntityManagerFactory emf;

    public CacheEvictionScheduler(EntityManagerFactory emf) {
        this.emf = emf;
    }

    // fixedRateString reads the interval from a property; 300000 ms = 5 minutes
    @Scheduled(fixedRateString = "${app.cache.evict-interval-ms:300000}")
    public void evictAllCaches() {
        emf.getCache().evictAll();                 // clears the entire 2LC
        log.info("Hibernate second-level cache cleared (scheduled)");
    }
}
    • Enable scheduling once on a @Configuration class (or the main app class):
    @org.springframework.context.annotation.Configuration
@org.springframework.scheduling.annotation.EnableScheduling
public class SchedulingConfig { }
    • TTL vs scheduled flush — which to use?
    Approach Granularity When to choose
    EhCache TTL/TTI (Option A) Per entry (each entry expires 5 min after its own write). Default choice — smooth, staggered eviction; no thundering herd.
    @Scheduled evictAll (Option B) All at once, every interval. Coarse cache invalidation tied to an external event/cadence; simplicity.

    ⚠️ A periodic evictAll() clears the cache for every entity at the same instant, so the first request after each flush hits the database for everything (a brief "cold cache" spike / thundering herd). Per-entry TTL avoids this because entries expire at different times. Prefer Option A unless you specifically need a synchronized wipe.

    Common Pitfalls#

    • Same-transaction testing. Repeated reads in one transaction hit L1, not L2 — you'll wrongly conclude the 2LC "isn't working" (Step 6).
    • Wrong EhCache jar. Missing the jakarta classifier → provider not found on Boot 3 (Step 1).
    • Forgetting @Cache. @Cacheable alone with ENABLE_SELECTIVE marks the entity, but Hibernate needs @Cache for the concurrency strategy; only the JPA marker may leave it effectively uncached depending on config — annotate with both to be safe.
    • Caching volatile data. Putting a frequently-updated entity in the cache adds eviction overhead for little benefit. Cache read-mostly data.
    • Query cache on hot tables. Constant invalidation makes it slower than no cache.
    • Scheduled evictAll thundering herd. A periodic full flush (Step 9, Option B) empties every region at once, so the next requests all miss and hit the DB simultaneously. Prefer per-entry TTL for smooth, staggered expiry.
    • Distributed staleness. A simple on-heap EhCache is per-JVM. In a multi-instance deployment, node A's update doesn't evict node B's cache → stale reads. Use a distributed provider (Infinispan, Hazelcast, Redis/Redisson) for clustered correctness.

    Cache Provider Options#

    • The 2LC is provider-agnostic via JCache. Common choices:
    Provider Best for
    EhCache 3 Single-node apps; simple, fast, on-heap/off-heap. (This note.)
    Infinispan Clustered/replicated caching, JBoss/Quarkus ecosystems.
    Hazelcast Distributed in-memory data grid across many nodes.
    Redis (Redisson) Externalized, shared cache surviving app restarts; large datasets.

    Best Practices#

    • Cache read-mostly reference data first (READ_ONLY where possible) — that is where 2LC pays off most.
    • Choose the weakest correct concurrency strategy to minimize overhead.
    • Always verify with statistics or SQL logs; never assume the cache is hitting.
    • Set sensible TTL and heap limits per region — an unbounded cache is a memory leak.
    • Go distributed when you scale out to avoid cross-node staleness.
    • Disable generate_statistics in production (it has a small cost); keep it on in dev/test.
    • Prefer caching at the right layer: for full HTTP/response caching consider Spring Cache (@Cacheable) on the service layer; the Hibernate 2LC is specifically for entity/row reuse. They can be combined.
