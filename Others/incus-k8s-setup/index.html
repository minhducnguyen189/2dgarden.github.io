    Incus + Kubernetes Homelab — Setup Documentation#

    A self-hosted Kubernetes (HA) cluster and a Docker host, all running as Incus system containers on a single physical machine.

    Documented on 2026-06-14 by scanning the live Incus state and ~/.bash_history.

    This file is the hub — overview, current state, and reference. The step-by-step build runbooks live in four companion guides (follow in order): 1. ./k8s-master-incus-setup.md — HA masters + HAProxy 2. ./k8s-worker-incus-setup.md — worker nodes 3. ./k8s-control-master-incus-setup.md — admin / jump host 4. ./k8s-dashboard-incus-setup.md — web dashboard (Headlamp) + metrics-server

    1. Overview#

    Everything runs on one physical host (duc-MS-7E01) using Incus 7.0 to provide lightweight system containers. There are two independent workloads:

    Workload Containers Purpose
    Kubernetes (HA) kmaster, kmaster2, knode1, knode2, kapi-lb, kcontrol A 2-control-plane / 2-worker cluster with an HAProxy API load balancer and a dedicated kubectl box
    Docker docker-host A nesting-enabled container running Docker Engine + Compose, with NVIDIA GPU passthrough

    3. Incus setup#

    3.1 Installation (Zabbly repo)#

    Incus is installed from the official Zabbly LTS 7.0 APT repository (not the distro package), pinned to the LTS 7.0 train:

    URIs:   https://pkgs.zabbly.com/incus/lts-7.0
Suites: resolute

    # (key + sources file written to /etc/apt/sources.list.d/zabbly-incus-lts-7.0.sources)
sudo apt-get install incus

    Note from history: a previous Docker / Podman / older-Incus install was fully purged before this clean setup (apt purge podman ... docker-ce ..., rm -rf /var/lib/incus /etc/incus).

    3.2 Initialization (incus admin init)#

    Incus was initialized from a preseed file — incus-admin.yaml (kept in this directory). Key choices:

    Setting Value Meaning
    core.https_address 192.168.1.214:8443 Remote REST API exposed on the LAN
    Storage pool local (driver dir) Plain directory-backed storage
    Default profile root disk pool local, path /
    cluster.enabled true Single-member "cluster" (server_name: duc-MS-7E01) 
    incus admin init        # interactive, or: cat incus-admin.yaml | incus admin init --preseed

    3.3 Storage pool#

    NAME    DRIVER   USED BY
local   dir      9

    A single dir-backed pool named local holds the root filesystems of all instances. Simple and portable (no ZFS/btrfs/LVM dependency).

    3.4 Network (incusbr0)#

    A single managed bridge provides networking for every container:

    name: incusbr0
type: bridge
config:
  ipv4.address: 10.177.167.1/24   # gateway / DHCP range for containers
  ipv4.nat: "true"                # masquerade out to the LAN/internet
  ipv6.address: none              # IPv6 disabled

    incus network create incusbr0 ipv4.address=auto ipv4.nat=true ipv6.address=none

    All 7 instances attach to incusbr0 and receive 10.177.167.x addresses via Incus's built-in DHCP.

    The physical interfaces enp4s0 and wlo1 appear in incus network list as unmanaged (MANAGED: NO) — they are just the host NICs, not used directly by the containers.

    3.5 Profiles#

    There are two profiles:

    default — used by docker-host#

    config: {}
devices:
  eth0: { name: eth0, network: incusbr0, type: nic }
  root: { path: /, pool: local, type: disk }

    k8s — used by all 6 Kubernetes containers#

    This profile makes a stock container able to run kubelet + containerd + a CNI.

    config:
  limits.cpu: "2"
  limits.memory: 2GB
  limits.memory.swap: "false"            # k8s requires swap off
  linux.kernel_modules: ip_tables,ip6_tables,netlink_diag,nf_nat,overlay,br_netfilter
  security.nesting: "true"               # run containers inside the container
  security.privileged: "true"            # needed for kubelet/containerd bits
  raw.lxc: |
    lxc.apparmor.profile=unconfined
    lxc.mount.auto=proc:rw sys:rw
    lxc.mount.entry=/dev/kmsg dev/kmsg none bind,create=file,mode=0666 0 0
devices:
  eth0: { name: eth0, nictype: bridged, parent: incusbr0, type: nic }
  root: { path: /, pool: local, type: disk }

    Each k8s container therefore gets 2 vCPU / 2 GB RAM, swap disabled, the kernel modules kubelet needs, and the host-level relaxations (see §6.6 for why each line is needed).

    5. Docker setup (docker-host)#

    A single container dedicated to Docker workloads, kept separate from the Kubernetes containers.

    Launch (with nesting):

    incus launch images:ubuntu/24.04 docker-host -c security.nesting=true

    Current config highlights (incus config show docker-host --expanded):

    Setting Value
    Base image Ubuntu 24.04 (noble)
    security.nesting true (required to run Docker inside Incus)
    security.privileged true
    nvidia.runtime false
    GPU device type: gpu, gputype: physical, pci: 0000:01:00.0
    Profile default

    GPU passthrough was added with:

    incus config device add docker-host gpu gpu gputype=physical pci=0000:01:00.0

    Software inside:

    • Docker Engine 29.5.2
    • Docker Compose v5.1.4
    • Installed from Docker's official APT repo (download.docker.com)

    Networking inside the container: Docker creates its usual bridges — docker0 (172.17.0.1) and a per-Compose-project bridge (br-… 172.18.0.1). These live inside docker-host and are NAT'd out through eth0 (10.177.167.12).

    Currently running: one container — coolercontrold (coolercontrol/coolercontrold, port 11987).

    A large library of Compose stacks (Immich, Jellyfin, Komga, Homarr, FreshRSS, SearXNG, Open WebUI, Guacamole, etc.) exists in the user's ~/server/docker repo; those are deployed onto this Docker host as needed.

    6. Kubernetes setup#

    6.1 Cluster topology#

    A highly-available cluster built with kubeadm:

    • 2 control-plane nodes with stacked etcd — kmaster, kmaster2
    • 2 workers — knode1, knode2
    • 1 API load balancer — kapi-lb (HAProxy)
    • 1 management box — kcontrol (holds admin kubeconfig)
    kubectl (kcontrol / host) ──▶ 10.177.167.222:6443 (kapi-lb / HAProxy)
                                      │  roundrobin, tcp-check
                          ┌───────────┴───────────┐
                          ▼                        ▼
                  kmaster :6443             kmaster2 :6443
                  (apiserver+etcd)          (apiserver+etcd)
                          ▲                        ▲
                          └────────── join ────────┘
                                  knode1, knode2

    kubectl get nodes -o wide:

    NAME       STATUS   ROLES           VERSION    INTERNAL-IP
kmaster    Ready    control-plane   v1.33.12   10.177.167.26
kmaster2   Ready    control-plane   v1.33.12   10.177.167.33
knode1     Ready    <none>          v1.33.12   10.177.167.228
knode2     Ready    <none>          v1.33.12   10.177.167.118

    6.2 Versions & runtime#

    Component Version
    Kubernetes (kubeadm/kubelet/kubectl) v1.33.12
    Container runtime containerd 1.7.24 (Debian package)
    CRI socket unix:///run/containerd/containerd.sock
    Node OS Debian 13 (trixie)
    Image repository registry.k8s.io

    containerd was configured with a generated default config before init:

    sudo mkdir -p /etc/containerd
containerd config default > /etc/containerd/config.toml
sudo systemctl restart containerd && sudo systemctl enable containerd

    kubeadm / kubelet / kubectl were installed from the official pkgs.k8s.io repo (the v1.3x stable channel) and held at their version:

    sudo apt-get install -y kubelet kubeadm kubectl
sudo apt-mark hold kubelet kubeadm kubectl
sudo systemctl enable --now kubelet

    6.3 Cluster networking (Flannel)#

    From the kubeadm-config ConfigMap (ClusterConfiguration):

    Network CIDR / value
    Pod subnet 10.244.0.0/16
    Service subnet 10.96.0.0/12
    DNS domain cluster.local
    Control-plane endpoint 10.177.167.222:6443

    CNI: Flannel, VXLAN backend (kube-flannel-cfg ConfigMap):

    { "Network": "10.244.0.0/16", "EnableNFTables": false, "Backend": { "Type": "vxlan" } }

    Each node runs a kube-flannel-ds pod; pods get addresses out of the per-node 10.244.x.0/24 ranges (visible as cni0 / flannel.1 interfaces on the nodes). CoreDNS runs with 2 replicas in kube-system.

    kubectl get pods -A (summary): kube-flannel (4× ds), kube-system (2× coredns, 2× etcd, 2× apiserver, 2× controller-manager, 2× scheduler, 4× kube-proxy) — all Running.

    6.4 HA API load balancer (kapi-lb)#

    kapi-lb runs HAProxy and is the single front door to the API server. Its address 10.177.167.222:6443 is the cluster's controlPlaneEndpoint, so every kubectl call and every node joins through it.

    /etc/haproxy/haproxy.cfg:

    frontend kubernetes-frontend
    bind *:6443
    mode tcp
    option tcplog
    default_backend kubernetes-backend

backend kubernetes-backend
    mode tcp
    option tcp-check
    balance roundrobin
    server kmaster  10.177.167.26:6443 check
    server kmaster2 10.177.167.33:6443 check

    TCP pass-through (mode tcp) — HAProxy does not terminate TLS; it just round-robins between the two apiservers and health-checks them.

    6.5 Management box (kcontrol)#

    A dedicated container for running kubectl against the cluster, so the admin credentials don't have to live on a control-plane node. It was set up by copying the admin kubeconfig off kmaster:

    incus exec kcontrol -- mkdir -p /root/.kube
incus file pull kmaster/etc/kubernetes/admin.conf .
incus file push admin.conf kcontrol/root/.kube/config
    • Current context: kubernetes-admin@kubernetes
    • API server it talks to: https://10.177.167.222:6443 (i.e. via kapi-lb)

    6.6 Why the special k8s profile#

    Running kubelet/containerd inside an unprivileged system container normally fails. Each line in the k8s profile fixes a specific problem:

    Profile setting Why it's needed
    security.nesting=true Lets containerd run containers inside the Incus container
    security.privileged=true kubelet/containerd need broad capabilities & device access
    limits.memory.swap=false kubelet refuses to start with swap on
    linux.kernel_modules=…,overlay,br_netfilter,… overlayfs for images; br_netfilter + iptables for pod/service networking
    raw.lxc: lxc.apparmor.profile=unconfined AppArmor would block many container operations
    raw.lxc: lxc.mount.auto=proc:rw sys:rw kubelet/CNI need writable /proc and /sys
    raw.lxc: …/dev/kmsg… kubelet reads /dev/kmsg; it doesn't exist in containers, so the profile tries to bind-mount it in (see note below)

    /dev/kmsg — two mechanisms, one winner. The profile line above bind-mounts /dev/kmsg, but each node also runs a kmsg-symlink.service (created in the build guides) that recreates /dev/kmsg as a symlink to /dev/console before kubelet starts. On the live nodes that systemd service is the mechanism actually in effect (/dev/kmsg -> /dev/console, service enabled). Keep the service; the profile line is harmless redundancy.

    Host-side sysctl (set on the host, applies to bridged traffic) from history:

    # /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1

    7. Build order & runbooks#

    The full step-by-step instructions live in the three companion guides. Build in this order — each assumes the previous one is done:

    Order Guide What it covers
    0 (this file, §3) Install Incus, create incusbr0, the local pool, and the k8s profile
    1 ./k8s-master-incus-setup.md Host kernel prep, kapi-lb (HAProxy), kmaster + kmaster2, kubeadm init, Flannel
    2 ./k8s-worker-incus-setup.md Provision a worker (knode1/knode2) and kubeadm join it via the LB
    3 ./k8s-control-master-incus-setup.md kcontrol admin/jump host: kubectl + helm + kubeconfig
    4 ./k8s-dashboard-incus-setup.md Web dashboard (Headlamp) + metrics-server, exposed via NodePort

    The guides are the single source of truth for the build steps; this file intentionally does not repeat them, so they can't drift apart.

    8. Incus-specific gotchas (read once, referenced everywhere)#

    Running Kubernetes in unprivileged-ish system containers needs several workarounds. Each is applied in the guides; they're collected here so the why is explained in one place.

    Gotcha Symptom if ignored Fix (where)
    Kernel modules can't be loaded from inside a container kubeadm/CNI fail on br_netfilter, overlay Pre-load on the host + list them in the k8s profile (master guide §1.1, profile)
    /dev/kmsg is masked by Incus kubelet crashes / won't start kmsg-symlink.service symlinks it to /dev/console before kubelet (master §4.4, worker §4.1) — see §6.6
    SystemVerification preflight can't verify kernel from a container kubeadm join/init errors out --ignore-preflight-errors=SystemVerification (master §5, worker §5.1)
    CNI plugin path: Debian's containerd scans /usr/lib/cni, not /opt/cni/bin pods stuck in ContainerCreating install plugins to /opt/cni/bin and mirror to /usr/lib/cni (master §6.2, worker §4.2)
    pause image mismatch extra image pull + warnings pin sandbox_image = registry.k8s.io/pause:3.10 in containerd (master/worker containerd step)
    kube-proxy conntrack maxPerCore is locked by the host kube-proxy errors set maxPerCore: 0 in the kube-proxy ConfigMap (master §6.4)
    kubectl version skew on kcontrol unsupported client/server gap pin kubectl to the cluster minor (v1.33) — control guide Step 1

    9. Useful day-to-day commands#

    Incus:

    incus list                              # all instances + IPs
incus profile show k8s                  # inspect the k8s profile
incus config show kmaster --expanded    # full effective config of a container
incus exec kmaster -- bash              # shell into a container
incus file push file.sh kmaster/root/   # copy a file in
incus restart kmaster

    Kubernetes (from kcontrol, or the host if kubeconfig is set):

    incus exec kcontrol -- kubectl get nodes -o wide
incus exec kcontrol -- kubectl get pods -A -o wide
incus exec kmaster  -- kubectl cluster-info
incus exec kmaster  -- kubeadm token create --print-join-command

    Docker host:

    incus exec docker-host -- docker ps
incus exec docker-host -- docker compose version

    Generated by scanning the live Incus state and shell history. IPs are DHCP-assigned by incusbr0 and may change on container recreation; the control-plane endpoint 10.177.167.222 (kapi-lb) is the stable entry point.
